# Baobook tests

End-to-end Playwright scenarios (Chromium). Each file is a standalone scenario. It prints `✓`/`✗` lines and exits with code 1 if anything fails. Every scenario serves `public/` over HTTP with the tiny static server in `lib/server.mjs` (Node only, no dependencies) on `127.0.0.1` with a random port. The app needs a real origin: its language files load with `fetch`, which does not work from `file://`, and the service worker only runs over http(s). Each server is its own origin with its own storage. Every browser context gets `CTX` from the same module: the Ukrainian locale (the checks read Ukrainian UI strings) and clipboard permissions.

```sh
cd /path/to/baobook
npm i --no-save playwright@1.63.0 && npx playwright install chromium   # once; node_modules is gitignored; CI pins the same version
node tests/apparea.mjs
```

The scripts are ES modules, so `playwright` must be in `node_modules` at the repository root (or a symlink or junction to another folder that has it).

The `CHROMIUM` environment variable is the path to a Chromium binary. Without it, the scripts use `/opt/pw-browsers/chromium` if it exists (Claude Code cloud environment), otherwise Playwright's own Chromium.

On Windows, Playwright's Chromium download may time out; use an installed browser instead:

```powershell
$env:CHROMIUM='C:\Program Files\Google\Chrome\Application\chrome.exe'; node tests/appchip.mjs
```

Desktop Chrome on Windows differs from Chromium on Linux in two ways that matter here. It supports the Web Share API with files, so `appsave` stubs `navigator.share`/`canShare` and checks both paths. Its system font, Segoe UI, has taller line boxes, so the bottom panels on touch are a few pixels taller than on Linux. Layout checks compare elements with each other, never with fixed pixel values.

The sync core (`public/sync.js`, `docs/SYNC-PLAN.md`) is also tested without a browser: `sync*.mjs` load it in Node through `lib/core.mjs` and run it over an in-memory transactional store (`lib/memstore.mjs`) and the test cloud (`lib/cloud.mjs`): the adapter contract with a virtual clock, faults by name (`lost`, `fail`, `delay`, `late`, `dup`, `reorder`, `tworunners`, `other`, and `hold`, which keeps one `get` or one transaction in flight until the scenario resolves its promise; per device and per call), and the checks the security rules will make. The browser scenarios `appsync`, `appsend`, `apprecv`, `apptotals`, `apprevive`, `apptomb`, `appleader`, `apptablrev`, `appeditor` and `appbfcache` share one test cloud across several browser contexts («devices») through `lib/cloudpage.mjs` (the cloud transaction crosses `exposeBinding` in two calls; `newTab` opens a second tab of the same device, `lead` and `locks` read the leadership and the Web Locks) and drive the engine through the `sheetDebug.sync` hook. `syncsim.mjs` takes `SEEDS=1,2,3` and `OPS=400`; `TRACE=<id>` prints the operations touching a note and `STATE=1` the final state of every device.

The Firestore security rules (`firestore.rules` at the repository root, `docs/SYNC-PLAN.md` §4.16) are tested on the Firestore emulator by `rules/firestore.mjs`. It has a folder of its own with its own `package.json` and lock file (`firebase-tools`, `@firebase/rules-unit-testing` and `firebase`, all pinned), so the Playwright scenarios (every `tests/*.mjs`, with `playwright` in the root `node_modules`) do not pick it up and the root keeps no `package.json`. The emulator needs Java 21 or newer. It runs under the demo project id `demo-baobook`, so no request reaches the real Firebase project:

```sh
cd tests/rules
npm ci     # once: its own node_modules, firebase-tools included
npm test   # = npx firebase emulators:exec --only firestore --project demo-baobook "node firestore.mjs"
```

The emulator listens on `127.0.0.1:8080` (`firebase.json`) and is downloaded into `~/.cache/firebase/emulators` on the first run. The test puts its own uid into the access list of `allowed()` (the owner's uid, in the file since 3c) and empties the emulator before each scenario. On Windows, Oracle's `javapath` launcher on `PATH` leaves the emulator's Java process running after the test, and the next run finds port 8080 taken: put the JDK's own `bin` first (`$env:PATH='C:\Program Files\Java\jdk-21\bin;'+$env:PATH`) or stop that process.

The Firestore adapter (`public/cloud.js`, the cloud adapter contract of `docs/SYNC-PLAN.md` §4.6) is tested on the same emulator by `rules/adapter.mjs`, over the npm package of the SDK (the same version the app loads from gstatic) and an authenticated instance from the rules test library; `npm test` in `tests/rules` runs both files.

The scenarios on the **Auth and Firestore emulators** live in `tests/emu/` (outside the `tests/*.mjs` loop of the Playwright job; their own CI job `sync-emulator`). They run from `tests/rules`, which holds `firebase-tools`, with Playwright from the repository root:

```sh
cd tests/rules
npx firebase emulators:exec --only auth,firestore --project demo-baobook "node ../emu/smoke.mjs"
for f in ../emu/*.mjs; do npx firebase emulators:exec --only auth,firestore --project demo-baobook "node $f"; done   # every scenario, a clean emulator each
```

While working on them it is faster to keep the emulators up (`npx firebase emulators:start --only auth,firestore --project demo-baobook` in `tests/rules`) and run the scenarios directly; each one clears both emulators when it starts, so they run one at a time.

`emu/lib/emu.mjs` drives the emulators by REST alone, so the Node side needs no `firebase` package: clearing both emulators, a Google user from a fake id token (`accounts:signInWithIdp` on the Auth emulator; the emulator assigns the uid), the repository's rules loaded with that uid (`PUT …:securityRules`), documents seeded past the rules with timestamps (`Authorization: Bearer owner`). The browser loads the Firebase SDK the way the app does, from `www.gstatic.com/firebasejs/<version>/`, but a route serves the three files from `tests/emu/.sdk/<version>/` (downloaded once with `curl`, gitignored, cached in CI); every other request to a Google host is aborted and counted, and a scenario fails if one was made. The contexts block service workers, since a route does not see the worker's own fetches. The browser signs in with `GoogleAuthProvider.credential('{"sub":…,"email":…}')`, which the Auth emulator accepts; the same `sub` is the same user. The SDK version is `SDK_VER` in `emu/lib/emu.mjs`. `emu/lib/app.mjs` runs the app itself on the emulators: a «device» is a context with the `emulator` flag (and a short pace) put into the settings before the first start, so the app on 127.0.0.1 takes the demo project (`FB_EMU` in `index.html`); the sign-in goes through the app's test hook `sheetDebug.sync.signIn(credential)`, everything after it is the app's own code; `menu()` reads the account menu and the status button as the user sees them, `untilUI()` waits for a status code.

The stamp: `v`, `rev` = old + 1, `srv` = the server time, `op`, `dev`, `dn`. Receipts: the own one equals `op`, other devices' ones cannot change or go, at most 200 (device 201 is refused). Keys and types of a note, a tombstone and a version. The trash is dated by the server: `tsrv` on entering and extending it, kept by an edit there, dropped by a restore, never moved back. A tombstone is final; a manual one is allowed, the automatic purge only 30 days after `tsrv` (refused just after trashing, at 29 days, without `tsrv`, outside the trash, and after another device restored the note). A version needs a note that is not purged to be created or renamed; a rename changes only the name and the stamp; a deleted version stays deleted; deleting a version is allowed after its note is purged; a version's note id may have up to 64 characters |

GitHub Actions (`.github/workflows/tests.yml`) runs the same scenarios on every PR and on pushes to `main`; screenshots from the run are in the `tests-screenshots` artifact. A second job, `firestore-rules`, runs `rules/firestore.mjs` and `rules/adapter.mjs` on the Firestore emulator with Java 21 and the pinned `firebase-tools`. A third, `sync-emulator`, runs `emu/*.mjs` on the Auth and Firestore emulators with Playwright, caching the emulators and the SDK files.

Run scenarios one at a time. `appdrop` 5a/5b (mouse drag with coordinate checks) failed once while two other scenarios ran in parallel and passes reliably on its own. This may be test flakiness under load; an app bug is not proven.

Wait for a condition, not for a fixed pause: a pause that is long enough on a quiet machine can be too short on a busy one. `lib/wait.mjs` has `ready` (the app has started and drawn the note list), `frames`, `still` (no CSS transition left in an element), `resize` (a new viewport size has reached the page and its resize timers), `armClick`/`clicked` (the click a tap causes on an element has been handled) and `until` (polls a value; the check after it still decides). These helpers rely on frames and timers, which a background tab throttles: bring the page to the front first. To shake out such races, run a scenario while three or four others run in parallel, or with the renderer slowed down through a CDP session (`Emulation.setCPUThrottlingRate`).

Scenarios write screenshots and temporary files to `<tmpdir>/sheet-tests/`, not into the repository.

To reset state between steps, run `localStorage.clear()` + `indexedDB.deleteDatabase('sheet')` after a pause of at least 400 ms (autosave has a 300 ms delay).
