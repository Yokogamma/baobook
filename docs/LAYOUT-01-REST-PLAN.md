# The rest of layout 0.1 (plan)

Status: **proposed, 2026-11-27; revised after two rounds of the independent review the same day, the second answered by the narrow architecture review of §7 (review log); not approved.** Written against `main` at `07966f4` (build 2026112701), after the stage of [`LAYOUT-SEAMS-PLAN.md`](LAYOUT-SEAMS-PLAN.md) closed (#160–#178). Everything here that rests on no decision of the owner is a proposal; the owner's questions are in §3, each with a recommendation. Decisions are cited by their ids in `LAYOUT-MODEL.md` §2 (G27, W13…), rules by theirs in `LAYOUT-RULES.md` (DRAG.B4, RESIZE.1…), the seams plan's questions as Q1–Q10.

## 1. Why a new plan

`LAYOUT-ENGINE-PLAN.md` §5 planned steps 3–6 before the slice existed. The slice built much of steps 3–5, and built it otherwise: the page keeps its own commands and asks `bridge.page()` what they were for the engine, instead of one `LAYOUT.change(…)` per call site (engine plan §6, item 1); `ops.js` has the exact undo only; `measure.js`, `view.js` and `page.js` are wired behind the switch with no `input.js`. Rewriting §5 in place would erase the record of what was approved, and the seams plan is closed. So this document plans what remains, and the engine plan's §5 gets one line pointing here. The engine plan's §3 (data), §4 (determinism, bounds, measuring, passports, budgets), §6 (the boundary, its table of commands and §6.4's undo as G27 amends it) and §7 (risks) stay the reference; where this plan and them differ, this plan says so, and it wins.

The rules that carry over:

- **Build on the slice, not beside it.** `page.js` stays the one object `index.html` calls; `bridge.page()` stays the boundary for the page's own commands, and anything the engine has no action for ends in `outside` (opened again, nothing written). A command gets an action of its own only by a PR of this plan, never by a second path around the bridge.
- **One note is never served by two layouts in one tab**; the switch is read once when a tab starts (engine plan §1).
- **No change of the stored format** in 0.1 (engine plan §1, §3); a refused or failed layout writes none of its places; what is typed is saved whatever SETTLE answers (seams plan §8).
- **The process of the seams plan §9** (the owner's Q6): a finding is first a minimal permanent case, then its class in the generator with a saved seed; reachable means a sequence of allowed commands from a valid state; two rounds with findings of one class start an architecture review.
- **Every PR** into `main`, reviewed, merged on the owner's word; one that changes `public/` raises `BUILD` and runs `node tests/hashes.mjs --write`; a new file under `public/layout/` gets its SRI row by hand; a new test file gets its row in `tests/README.md`, and a weight in `tests/lib/shard.mjs` when slow.

### D1. G27's undo (B), pure

`ops.js` `undo` gets its second path, in a module of its own, `public/layout/reconcile.js`, since D4 uses the same pass.

- **The entry** gains `ran`, the containers its action ran in (`commit` has it and keeps it today only for the write), and keeps the canonical tree before (`canon`, §7) beside the tree shown before (`tree`) and the temporary rows that were in effect then (`temps`), with `before`, `after`, `fields` and `signs`; `signs` are the canonical signatures of §7, taken as §7 says.
- **The exact path first**, as built: the identity is the top entry's `after` and every recorded signature is today's. It puts back the stored fields before as the entry holds them, and the tree before: `tree` itself when today's temporary rows are the entry's `temps`, otherwise `display(canon, today's temporary rows)` (§7); in both cases a place `open()` had repaired and the action had not written included, a difference between the shown and the stored that existed before the action exists again, and the identity becomes the entry's `before` (a temporary height is no change of identity, §6.4).
- **Otherwise (B)** (seams plan §7, G27): the candidate is the entry's canonical tree before the action (`canon`) with today's content, each block's own temporary rows (`tx`) today's (the current tree's for a block it holds, none for a block only the entry holds); the queue is made beforehand from it: the areas in reading order, in each its blocks in reading order, then the sheet's. Each block whose signature differs from the one the entry recorded gets an ordinary `{type: 'size'}` through `settleTree`, one RELINK each, on the canonical measure (`canonicalCtx`), children included; the canonical result is what is written and kept as the note's `canon`; then the temporary heights now in effect are shown on it by `display` (§7, Q22), not by `show`, which keeps widths; then `validate`, of the canonical tree and of the shown one. The queue's order is part of the contract (seams plan §7.1). The result gets a fresh identity. An empty queue (every signature equal, the identity not the entry's `after`) puts back `display(canon, today's temporary rows)` and still gets a fresh identity.
- **One step**: the check that the entry is the top of the stack, that the note's state is the one it was prepared on (its epoch and identity) and that the Measure's inputs have not changed (`version()`), the preparation, and the application are one call; a refusal or a failure keeps the entry, the state and the stored fields as they were (`{ok: false, why}`, the entries kept; Q17). A composite action (enter, leave, ungroup, an area's handle) is undone by its whole tree before, never by an inverse path.
- **The write**: `diff` of the stored fields against the canonical result, for the containers in the entry's `ran` and those the pass settled, and no other: a repair `open()` made in another container stays unwritten. The blocks the action made are removed; those it deleted are `restored` (their content the page's, their signatures today's).
- **What drops the entries**, as now: a change from outside (`outside`), the safe mode, a change of the rules (D14).

Tests, `tests/layoutreconcile.mjs` (Node), named: the lab's histories (`tests/lab/undo-snapshot/`): seed 101976 (typed over and back, (B) runs nothing); the review's case of seams plan §7 (C at row 8, both trees valid); the history `inverse` fails (two carries, typing between, the undo of the second); a signature that returns to its recorded value; a deleted block whose chip is relabelled (engine plan §6.4's X and N); the `MAXCELL` refusal that keeps the entry; a refusal on the second size of the queue after a first that succeeded, everything as before; an empty queue with a changed identity; two and three undos in a row with typing between; enter and leave followed by typing; one of the 25 histories whose answer depends on the queue's order, pinned; two areas, an empty queue of signatures and a repair pending in the area the action did not run in, which stays unwritten (the patch checked container by container); an exact undo after which the repair `open()` made before the action is again shown and unwritten. ### D3. The page's structural commands as the engine's actions

The slice drops the engine's entries on anything but a carry, enter and leave. Here every structural command of the page in the engine plan's §6 table becomes an engine action whose token the page's own stack keeps (`layUndo`), and typing no longer drops the entries (G27):

- deleting a block (the menu, Backspace in an empty block), an area with its children: `remove`; clearing the sheet: every block taken away as one action and one entry (today it calls `remove` block by block);
- `+`, a paste on the sheet, «блок після», an area by its button: `create` at its cell;
- converting to code or to text: a size change with the new passport, the bridge keeping the block's box by its id across the page's rebuild (today `outside`);
- collapsing and opening an area, a code block's own «more», `wrap` and `num`: a size change, written (`collapsed` and `open` are place fields);
- ungrouping: `ungroup`;
- restoring a block from «Історія»: a size change while it exists, `create` at its stored cell when it does not (engine plan §6).

**The command said, not guessed.** `bridge.page()` tells a command apart by what changed on the page, and `changed: id` alone cannot tell typing (no entry) from a structural size change of the same block (`wrap`, `num`, «more», a collapse: an entry). `page.js` `settle` gets the command's kind from the page (`settle(b, {act: 'size'})` and the like); with none it is typing as now.

**One undo, two owners, applied together.** The page holds the content and the engine the places, and one entry of the page's stack holds both. Its undo runs in this order: (1) the page prepares the content of the blocks the undo brings back without touching the page: their elements built apart, not in `blocks`, not drawn, so that `view.js`'s probe measures them as it measures a block (for a child still on the page, after an ungroup, its current text); (2) the engine prepares the whole result (D1) and checks it; (3) only when it is accepted, the page puts the content in and the engine's write on the blocks, `update()` and `markDirty()` once, and the entry is taken off. A refusal at (2) leaves the page, the stored note and the stack as they were, and says «Не вдалося скасувати» (a new key in `uk.json` and `en.json`; Q17). Today's `restoreArea` makes the area, moves the children, and calls `update()` and `markDirty()` before anything could refuse, so with the switch on it is replaced by this order.

**A version viewed.** `showVersion` and `showNow` redraw the blocks today, and `page.batch` ends in `reopen()`, which drops the stacks and the entries. With the switch on, `page.js` keeps the live note (tree, stacks, entries) aside while a version is shown, draws the version read-only by `open()`, and on leaving puts the live note back, or opens it again when it changed from outside meanwhile (engine plan §6.1).

**The signatures of what comes back.** A block the command deleted is gone from the page when the engine commits, so its signature is the one the Measure last measured it with, before the command (§7); the content prepared for the undo is signed by the same function, so a block brought back with nothing changed takes the exact path with the identity `before`.

**The budget.** An entry passes its size to `offerUndo` (engine plan §6.4); when an entry leaves the page's stack by any of its limits (`UNDO_MAX` per note, which `offerUndo` applies before `trimUndo`, `UNDO_TOTAL`, `UNDO_BYTES`), or a stack is dropped (`undoStale`), the engine's entry it held is dropped from `doc.undo` too, so no unreachable tree before stays in memory.

Tests: `tests/layoutbridge.mjs`, named: each command, its undo with nothing between (exact) and after typing ((B)), an undo refused; an area deleted with a child whose chip links to a note renamed before the undo: on success the area and the child come back together, the child at the height of today's chip label, the geometry valid; on a refusal both stay deleted, nothing is written and the same entry is still on top for another try (the exact case of an area with a child, 4a, stays); an ungroup undone after its child was typed into; clearing a sheet of two blocks and an area as one entry, and its undo; `wrap` toggled (an entry) and a keystroke in the same block (none); a carry, a version viewed, the note shown again, the carry's exact undo; the same with a change from another tab while the version is shown (the entries dropped). The class: the page's random histories gain these commands, typing between an action and its undo, and versions viewed; the page's blocks read afresh after every step giving the bridge's fields; a series of a hundred actions on the generated note of 120 blocks, the entries of `doc.undo` never more than the page's stack holds (past `UNDO_MAX` included) and their sizes within `UNDO_BYTES`; a block deleted and undone with nothing between: the exact path and the identity `before`. ### D5. Temporary heights through SETTLE (G26)

## 7. The canonical, the shown and the stored (the architecture review of D1, D5 and D6)

Two rounds of the review found findings of one class, the relation between the canonical, the shown and the stored geometry (round 1: D6's law; round 2: an undo under a temporary height, Q22, and the sheet's frame under a re-measure, Q21), so by the seams plan §9 this is a narrow architecture review of the three, on the review's two examples, not a rewrite. What it found and what the plan now says:

- **Why `show` and `unshow` are not enough.** They keep the stacks and the widths and change only rows (layout.js: «the same stacks and widths»). That was right while a temporary height changed no width. G26 (в) made a temporary height a change SETTLE runs, so the container rests with it and an elastic neighbour may narrow (the review: a text at `Box.w` 8, two temporary rows beside it; `show` leaves 8, a size change gives 21, and `unshow` of that result gives 21 back). So `unshow` of a shown tree that SETTLE made under temporary heights is not the canonical layout, and `show` of a canonical tree is not what the user sees.
- **The canonical layout is kept, not derived from the shown one.** The note holds `canon` beside the shown tree. Two operations in `reconcile.js` relate them, both through `settleTree` with the queue's order of D1: `display(C, X)` gives each block its temporary rows of `X` as a size change (D5's path), from `C`; `fold(S)` ends every temporary row of `S` the same way. An action runs on the shown tree, as Q4 decided; its canonical result is `fold` of the shown result, which is what `diff` writes and what becomes `canon`. With no temporary rows both are the identity and nothing more runs, so the common case costs nothing.
- **An entry** keeps `canon` before, the shown `tree` before and the `temps` then. The exact path puts back `tree` when the temporary rows are the same, else `display(canon, today's)`; (B) reconciles `canon` and ends with `display`. Both write canonically.
- **The canonical signature.** What a block shows only for a while (the code editor's state, today in the card's `className`) leaves `sign` and goes to the block's temporary rows, so opening an editor changes no signature. An entry's signatures are those the Measure last measured each block of the tree before with (`measure.js` keeps them), never read from the page after the command, so a block the command deleted keeps its own, and the content prepared for an undo is signed by the same function.
- **The stored geometry and the law of reopening** (D6, Q21): the stored fields are the canonical layout of the containers an action wrote. A container `open()` shows as the session does is one whose stored fields are its canonical layout, and since `open()` computes an area's frame from its children's stored places, the sheet qualifies only with its areas. The law is stated with that precondition; making the whole note qualify would mean writing what a re-measure moved, which §3.4 forbids.
- **Laws** (proposed, for the sequences): `fold(display(C, X)) = C`, rows and widths (L15); what is written is `fold` of the shown result (L16); the law of reopening under its precondition (L17), its containers counted apart.
- **Not changed:** the core, GAP's two measures in one tree (rows `y` and `yc` stay), Q4, and §3.4. `show` stays for `open()` with temporary rows (G26's case) and for an area's frame.

Asked of the independent review: whether these operations close both examples, and whether `fold` can refuse where an action was accepted (ending temporary rows only widens blocks back and lifts rows, so a refusal there is a bug and the action is then refused whole).

## 8. How the work is run (proposed)

The owner's wish of 2026-11-27: this plan's session is the controller, and the PRs are built in child sessions, so that the thread of the work is kept in one place.
