# Backend comparison: Firebase, Cloudflare, Laravel

**Status: a comparison for the owner's decision (2026-10-20), asked for after [MCP-PLAN.md](MCP-PLAN.md); nothing is decided or changed.** It compares three places for Baobook's server side across sync, sign-in and authorization, backups and MCP, and ends with a scorecard (§7) and a recommendation (§8). The facts were checked on 2026-10-20 against the sources in §10 and the research behind MCP-PLAN §3. **An independent review the same day** found the first version over-credited Cloudflare: it took point-in-time recovery for an undo, scored Firebase on Spark while letting Cloudflare move to a paid plan, overstated the cost of switching later, and gave no size for the rebuild. This version takes those corrections; the result is a near tie (§7), and the recommendation changed with it. **The owner's answer of 2026-10-20:** a VPS of the owner's is available for Laravel, and deploying to it is no problem; §6–§8 count Laravel on that VPS.

## 1. The question and what does not change

Baobook stays a local-first PWA: the main copy of the notes lives in IndexedDB on each device, the app works offline and without an account, and the static site stays on Cloudflare Workers Static Assets. The sync core in `public/sync.js` stays too: it talks to the cloud only through the adapter contract of SYNC-PLAN §4.6 (`get`, `txn`, `page`, `listen`, `totals`, `scan`), and its merges, receipts, tombstones and the totals check do not depend on Firestore. The question is only **where the shared copy lives and what enforces access to it**:

| Stack | Shared copy | What enforces access | Sign-in | Server code |
|---|---|---|---|---|
| **Firebase** (today, on .dev) | Cloud Firestore, Standard edition, `eur3`; Spark now, Blaze before the first outside user (SYNC-PLAN §2) | Firestore security rules (`firestore.rules`) | Firebase Auth, Google | none for sync; a small Worker for `/__/auth/*`, later the Drive token broker (BACKUP-PLAN B2) and MCP (MCP-PLAN) |
| **Cloudflare** | a Durable Object with SQLite storage per (env, user), in the EU jurisdiction | the Worker's own code in front of the object | Firebase Auth kept for Google sign-in (Cloudflare has no end-user sign-in service); the Worker verifies its ID tokens | a Worker + a Durable Object class |
| **Laravel** | a SQL database (Postgres or MySQL) behind a Laravel app | Laravel's own code (policies, middleware) | Firebase Auth kept (ID tokens verified in PHP), or replaced by Socialite + Sanctum | a Laravel app on the owner's VPS |

**Spending levels.** Each stack is judged at a comparable level: Firebase on **Blaze** with a budget alert (already planned in SYNC-PLAN §2 and BACKUP-PLAN), Cloudflare on **Workers Paid** ($5 a month; MCP-PLAN expects it anyway), Laravel on **the owner's VPS**, which exists already. Neither Blaze nor Workers Paid caps spending by itself (Blaze: documented; Workers Paid: no cap found); the VPS costs what it costs now. On the free tiers the picture changes as §7 notes.

## 2. Sync

| | Firebase | Cloudflare | Laravel |
|---|---|---|---|
| State | **built and tested**: PR 1–3c, the rules tested by 153 checks on the emulator, a randomized simulation, the account scenarios on the Auth and Firestore emulators; deployed on .dev; not on .app yet. Left: the owner publishes the rules, SYNC-CHECKLIST items 6–18 (the cost measurement included), PR 4–5 | to build (§6) | to build, in PHP, plus hosting |
| Writes | Firestore transactions from the client, retried on contention; the client sends `serverTimestamp()` as `srv` and the rules require `srv == request.time` | the adapter keeps `sync.js` unchanged by doing what a Firestore transaction does: read `D`, run `fn(D)`, then a write that succeeds only if `rev` is still the one read, else read and run again. The object checks the shape (the ported rules) and the `rev` precondition and writes in one synchronous `transactionSync`, with no `await` between check and write; tokens are verified in the front Worker, not inside the object; the receipt logic stays in the core | a database transaction with a per-user row lock |
| Order and completeness | `srv` is the request time, not the commit order, so the catch-up needs margins, and the totals check with a daily full pass is the guarantee (SYNC-PLAN §4.6) | `srv = max(now, last + 1)`, with `last` stored in the same transaction and one object for both collections, follows the commit order (`Date.now()` stands still between I/O events in Workers, so equal values are normal and `+1` separates them; the output gate holds the reply until the write is durable). Contract item 5 stays in the core, so the gain is fewer re-reads, not simpler code | the same as Cloudflare if every write of a user goes through one lock |
| Real-time updates | Firestore listeners, maintained by Google, re-authorized by the SDK | WebSockets into the object, with hibernation (an idle connection costs no duration; incoming messages billed 20:1 as requests); our code fans changes out, reconnects, and **re-authorizes**: a socket opened with a one-hour ID token must be closed or re-checked when the token expires, on sign-out, and when the uid leaves the allowlist | Laravel Reverb: for a few devices one process behind a reverse proxy (open-file tuning and Redis only matter past ~1 000 connections or several servers); managed on Laravel Cloud at extra cost; or polling |
| Limits that shape the code | Spark: 50 000 reads, 20 000 writes a day for the whole project, 10 GiB a month out, 1 GiB stored, hence the device budgets of SYNC-PLAN §4.17; on Blaze these become cost, not a stop; 1 MiB a document | Workers Free: 100 000 requests, 5 M rows read and **100 000 rows written** a day, where every index entry counts as a row (one note send ≈ 3–4 rows, so ≈ 25–30 000 sends a day, the order of Spark); on Paid, far beyond one owner. Per object 10 GB (1 GB on Free per the FAQ), 2 MB a row, 100 KB per SQL statement, 32 MiB per WebSocket message: all fit the 960 KiB note limit | the server's size and the database plan |
| .dev and .app | one database and one quota for both (SYNC-PLAN §6), separated by path only | separate Workers per env give **separate object namespaces**: separate data spaces and limits | separate apps or databases per env |
| Durability | multi-region `eur3` | each commit goes to five followers in different data centres and is confirmed by three | the database's own |
| Security model | declarative rules enforced by Google, written and tested | general code we write and test: the rules ported (shapes, `rev + 1`, receipts untouched, final tombstones, the trash date, the 30-day purge age, a version's live note), WebSocket authorization, and a schema migration per object when the format changes | the same, in PHP |
| Data location | `eur3` (Europe) | `jurisdiction("eu")` | the chosen region (Laravel Cloud: Frankfurt, Ireland, London) |
| If the cloud is down | the app works locally; sync waits | the same | the same |

| | Firebase | Cloudflare | Laravel |
|---|---|---|---|
| The owner's sign-in in the app | **built**: Google through Firebase Auth, popup and redirect, the `/__/auth/*` proxy for storage partitioning, checked on .dev; Apple possible later; free up to 50 000 monthly users | the same Firebase Auth; the app loads only its auth module; the Worker verifies ID tokens (BACKUP-PLAN B2 needs that code anyway). | The assistant's consent screen | on the app's origin, where the Firebase session already is (MCP-PLAN §6) | the same | on the Laravel host: one more sign-in unless the Laravel app sits under the same site |

## 4. Backups

Sync is not a backup (BACKUP-PLAN §1), and a server-side copy is a copy of the replica, not of the devices. **No stack's server-side recovery is an undo of a bad edit or merge:** every device keeps the bad state, and a cloud copy rolled back to an older `rev` is read by the devices as a stale server copy and quarantined (rule 1 of SYNC-PLAN §4.6), while documents written after the restore point vanish and are sent again from the devices. Server-side recovery is **disaster recovery for the cloud copy** (lost or corrupted data, a deleted account), followed by a procedure: restore, then on every device «Прибрати нотатки з пристрою» and a new sign-in so the devices take the restored state. Undoing a mistake stays with the history on the device and the dated copies of BACKUP-PLAN.

| | Firebase (Blaze) | Cloudflare | Laravel |
|---|---|---|---|
| Server-side recovery | scheduled backups, daily or weekly, kept up to 14 weeks, restored into a **new database**; point-in-time recovery for 7 days at one-minute steps (off by default, billing required), which also allows reading a path at a past time and writing it back | point-in-time recovery for 30 days per object, through an API (`getBookmarkForTime`, `onNextSessionRestoreBookmark`), applied to the whole object at its next restart; on by default per Cloudflare's 2024 announcement; **not available in local development**, so CI cannot test it; needs an admin endpoint of our own | scheduled database dumps (for example `spatie/laravel-backup`) to R2, S3 or Drive, set up and restore-tested by us; managed snapshots depend on the database |
| On Spark / Workers Free | none | not verified on Free | — |
| Copies the owner can open | BACKUP-PLAN B1–B4: dated copies made by the app into the owner's Drive while a device is open (7 daily, 4 weekly, 12 monthly); the manual export | BACKUP-PLAN unchanged; a nightly export of each object to R2 by a Cron Trigger is possible without any device open | dumps on a schedule without any device open; BACKUP-PLAN unchanged |

## 5. MCP (read-only `search` and `fetch`)

| | Firebase | Cloudflare | Laravel |
|---|---|---|---|
| Reading the notes | Firestore REST with a **service-account key** in a Worker secret; `roles/datastore.viewer` makes read-only a property of the credential, but the key reads every user and both envs | the MCP Worker calls the user's own object: **no key**, and the object id derived from the uid is the isolation; read-only becomes a property of **our code**: the MCP Worker gets a separate read-only RPC surface of the object and a static test that it calls nothing else | Eloquent queries on the same database: no key; isolation and read-only by our queries |
| Quota | on Spark it competes with sync for 50 000 reads a day and needs a mirror of the notes at Cloudflare (MCP-PLAN §7.6); on Blaze reads cost money instead (cents a day for one owner), so the mirror becomes optional | no competition worth counting | none |
| Search | the app's substring search, over every note or a mirror; Firestore Standard has no text search | the same search, or FTS5 in the same SQLite, next to the data | Postgres full-text (a Russian configuration, no Ukrainian dictionary) with `pg_trgm`, MySQL `FULLTEXT`, or the app's search ported to PHP |
| Where the notes are seen | Google (stored), Cloudflare (passing through; stored too if mirrored), the assistant's provider | Cloudflare (stored), the assistant's provider | the owner's VPS (and its hosting company), the assistant's provider |
| Protocol and OAuth code | libraries: `createMcpHandler` (MCP 2026-07-28 and older clients), `workers-oauth-provider` | the same | libraries: `laravel/mcp` 1.0 (2026-07-28 and legacy clients), Passport |
| Code of our own | the Firestore reader, the mirror on Spark, the text and search shared with the app, the consent page | the read-only RPC surface, the text and search shared with the app, the consent page | a PHP port of the app's text and search (two implementations to keep equal), the consent and user mapping |

| Operations | none of our own | a schema migration inside each object when the format changes; nothing else | PHP, database and package updates, monitoring, restore tests, on a server the owner already runs; one server, so its downtime pauses sync (the app works on) |
| Lock-in | Firestore's data model and rules | the site and the data on one provider (the Drive copies keep an exit) | the least: plain SQL and PHP |

## 7. Scorecard

1 is weak, 5 is strong, judged for this project (one owner now, a few invited users later) at the spending levels of §1; rows 1–4 and 6 judge the end state, row 5 the cost of getting there from today.

| Criterion | Firebase | Cloudflare | Laravel | Why |
|---|---|---|---|---|
| 1. Sync | **4** | **4** | **3.5** | Firebase is built and proven, bent around `srv` that is not the commit order; Cloudflare fixes the order and the quota but adds our own access code, WebSocket re-authorization and per-object migrations; real-time is a tie; Laravel gets plain SQL transactions and a Reverb process on one server, with the server code in a second language |
| 2. Sign-in and authorization | **4.5** | **4.5** | **3.5** | the first two share Firebase Auth for people and the same OAuth library for assistants; Passport through `laravel/mcp` has one scope and no advertised CIMD |
| 3. Backups | **3.5** | **4** | **4** | all three are disaster recovery for the cloud copy; Blaze's backups restore into a new database and keep 14 weeks; Cloudflare's 30 days per user come with no setup but only through an API that CI cannot test; dumps we schedule and test |
| 4. MCP | **3.5** | **4.5** | **4** | a project-wide key, though read-only by IAM; no key, read-only by our code; no key, but the app's search ported to PHP |
| 5. From today (5 = nothing to do) | **4.5** | **2.5** | **2** | the rules and the checklist; the cloud side of sync and its test infrastructure again; the same rebuild in PHP, the host already there |
| 6. Running and cost | **4** | **4** | **3.5** | both a few dollars a month at most and two platforms each; Laravel costs nothing new but is a server the owner keeps healthy |
| **Total of 30** | **24** | **23.5** | **20.5** | |

**How it moves.** Equal weights: 24 / 23.5 / 20.5. Row 5 counted twice: 28.5 / 26 / 22.5. **The end state alone (row 5 left out): 19.5 / 21 / 18.5.** On the free tiers (Spark against Workers Free) Firebase loses its server-side backups and needs the MCP mirror (backups 2.5, MCP 3: 22.5 in all), while Cloudflare keeps hard daily limits of the same order as Spark's. So: **Cloudflare has the better end state by a point and a half; any weight on what is already built gives Firebase the lead. Laravel is last under every weighting tried**, within a point of Firebase on the end state now that the VPS is there. What the scores leave out is control: on the VPS the shared copy is on a server the owner runs, not at Google or Cloudflare, and the server code is in PHP, which the owner knows; the price is a second language next to the app's JavaScript (the rules, the text and search for MCP) and one server instead of a platform.

## 8. Recommendation

- **Keep Firebase and release sync as built**: publish the rules, finish SYNC-CHECKLIST, and release `main → prod` when the owner asks. Move to **Blaze with a budget alert** when the first of these comes: server-side backups wanted, MCP on real notes, an outside user. On Blaze, MCP-PLAN's mirror becomes optional, and its service-account key stays the main cost of this choice (mitigated as MCP-PLAN §8.3–8.4 describe: viewer role, a key per env, rotation).
- **Cloudflare stays the documented alternative with the better end state.** Switching later is a planned re-upload from the devices, not a data migration (§6), so it need not be decided before the sync release. It is worth revisiting if Blaze's costs or quotas start shaping the code again, if the project-wide read key becomes unacceptable for MCP, or if .dev and .app should stop sharing one data space; the next step then is a design amendment to SYNC-PLAN (the object's API against the adapter contract, the ported rules, the WebSocket listener with re-authorization, CI) with the estimate of §6.
- **Laravel on the owner's VPS** is the choice if keeping the notes on the owner's own server matters more than the rebuild and a second language: it costs nothing new to host, its backups are ordinary database dumps the owner controls, and MCP reads the same database with no key. It needs the same rebuild of the cloud side as Cloudflare, in PHP, and a PHP copy of the app's text and search.

## 9. Not verified, and questions for the owner

- **Not verified:** point-in-time recovery, jurisdictions and WebSocket hibernation on Workers Free; «on by default» for point-in-time recovery outside the 2024 announcement; whether Workers Paid has any hard spending cap; the price of managed Reverb and whether Laravel Cloud's Postgres has point-in-time restore; whether Passport tokens carry the client or the resource as audience; latency from Ukraine to an EU object compared with `eur3` (not measured); whether `count`/`sum(rev)` in SQLite bills every row it reads (likely).
- **For the owner:** answered on 2026-10-20: a VPS for Laravel exists and deploying to it is no problem. Still open: how soon should sync reach .app? How much does it matter that the shared copy is on the owner's own server rather than at Google or Cloudflare? Is Blaze with a budget alert acceptable when backups or MCP need it? Is it acceptable, if Cloudflare is chosen later, that the site and the shared copy are with one provider, with the Drive copies as the exit?
