# No silent localStorage fallback when IndexedDB fails to open

**Status: plan, awaiting the owner's approval (2026-10-22); revised after four review rounds, the last one found no blocker or major issue (§12).** Nothing is implemented yet. One PR into `main` (§8 lists its parts), released with the next `main → prod`.

## 1. Problem

`db.init()` in `public/index.html` opens IndexedDB once (`idb.open()`); when the open fails it quietly switches the app to localStorage:

```js
try{ await idb.open(); db.backend='idb'; }catch(_){ db.backend='local'; if(LOCK) return; const w=await writerLock(); if(w) fbLocal(); else setLock(w===false? 'other' : 'nolock'); return; }
```

That mode was designed for a browser **without** IndexedDB (SYNC-PLAN §4.14, item 5: "a rare environment"). It is also what the app does when IndexedDB exists but one open fails, which Chrome on Android does from time to time: `UnknownError: Internal error opening backing store for indexedDB.open` at a cold start, after the system killed the browser under memory pressure, or right after the PWA was reinstalled. The next start usually opens the database fine. In the fallback mode:

- the real notes are not on the screen (they are in the database that did not open); the list shows only the localStorage copies, usually none, so `start()` runs `newNote()` and **stores an empty «Без назви» note** under a plain `sheet:note:<id>` key;
- the app is fully editable and looks normal; the only hint is «(резервне сховище)» in the storage line of the panel footer;
- the account menu and the status button are hidden (`accOn()` needs `db.backend==='idb'`), so to a signed-in user the app looks signed out and shows a strange empty list;
- at the next start with IndexedDB the plain keys move in (`db.move()`), and the stray empty note stays in the list for good (an empty note is only purged when it is deleted by hand).

The owner likely hit this on 2026-10-21 on Android after reinstalling the PWA from `baobook.matamata.dev` (not confirmed).

## 2. Evidence

Reproduced with Playwright on the current `main`. An init script wraps `IDBFactory.prototype.open`; while a flag is set it fails the open the way Chrome does — the call returns a request whose `error` event fires a moment later with `request.error` = `DOMException('Internal error opening backing store for indexedDB.open.','UnknownError')` — and, in a second run, by throwing the same DOMException synchronously out of `open()` (the `TypeError`/`SecurityError` shape). In `idb.open` these are two branches, `r.onerror=()=>{ … rej(r.error); }` and `catch(e){ return rej(e); }` in `go()`; both end in the same `catch` of `db.init()`, and both runs gave the same picture (the attempts are counted):

| Start | What the app did |
|---|---|
| 1. Normal start, a note typed | 1 note, stored in IndexedDB; `sheet:settings` gets `devId`, `devName`, `versSwept`; no `sheet:note:` keys |
| 2. The open fails | **one** attempt; the storage line says «1 нотатка на цьому пристрої (резервне сховище)»; the list shows one «Без назви»; the sheet is editable; no strip; a plain key `sheet:note:<new id>` holds the empty note |
| 3. Normal start again | 2 notes: the real one and the empty «Без назви» moved in from the plain key |

The scenario `tests/appidbfail.mjs` (§8) runs these steps and fails on the current code at steps 2 and 3.

The same open can also **hang** (no `success`, `error` or `blocked` event): Chrome's backing store open serializes behind the previous process's handles, and Safari had a known hang of the first `indexedDB.open` after a page was restored from the background. Today the app waits forever: the start never finishes, the sheet stays inert and the list empty, with no message.

## 3. Goal

- A device whose IndexedDB has worked before never silently drops into the localStorage mode: a failed open is retried, and if it still fails the app is **view-only with a strip that says why and offers a reload**, writes no note anywhere, creates no empty note, and recovers by itself when the storage opens again.
- A device that has never had IndexedDB keeps today's behaviour (the fallback mode with the writer lock, §4.14 of SYNC-PLAN).
- Nothing changes in the stores, the fields or the export format.

## 4. Behaviour

### 4.1 Starting

1. `db.init()` opens the database with **retries** for a failure that finishes and **one deadline** for a request that stays silent. The two are different in the browser: a request that fires `error` has left the origin's connection queue for `sheet`, so the next open can succeed; a request that never fires stays in that queue, and per the IndexedDB spec every later open of the same database — from this tab and from other tabs — waits behind it until it is processed. So:
   - **`error`** (Chrome's `UnknownError` comes this way; `VersionError` keeps its handling: another tab upgraded the database, open what is there) and a **throw** out of `indexedDB.open`: the attempt is retried after 300 ms and again after 900 ms, three attempts in all.
   - **Silence** — no event at all (`upgradeneeded`, `blocked`, `success`, `error`) within `OPEN_WAIT` = 8 s of the request: the attempt is abandoned and **no retry follows**, since it would only queue behind the hung request; the start goes to step 3 with `idb.silent=true`. The deadline is a silence detector, not a budget: the first event of a request clears it, so a slow upgrade on a fresh device (the `go(IDB_VER)` step that creates the stores) or a blocked request is never cut short; the second request of an attempt (`go(IDB_VER)` after the empty v1) gets a deadline of its own. A request that fires `upgradeneeded` and then never completes keeps the start waiting, as today: a deliberate hole (§9).
   - **`blocked`** is not a failure to retry: another tab holds the database, and `setLock('blocked')` after 3 s stays as it is.
   An abandoned attempt is **dead**: a flag checked first in `go()` (so a late `VersionError` starts no new chain), in `onsuccess` (the connection is closed, `done()` never runs, `idb.db` is not touched, no `go(IDB_VER)` upgrade starts; under the `storage` lock this late success is the storage coming back and is handed to `idbBack()`, §4.4), in `onerror` (swallowed; under the `storage` lock after silence it clears `idb.silent` and starts `idbWatch()`, since the queue is clear from that moment, §4.4) and in `onblocked` (no timer, no lock). A `success` of a live attempt ends the loop as today.
2. With the database open, the start goes on as today, and `S.idbOk` is written once (§5): this device has a working IndexedDB.
3. When every attempt failed:
   - no `window.indexedDB` at all, or the device has no marker (§5): **today's path**, unchanged — `db.backend='local'`, the writer lock, `fbLocal()`, or the `other`/`nolock` lock;
   - the marker is there: `setLock('storage')` **before** anything is written. `db.backend` stays `'local'`, so every path that asks for IndexedDB (`vstart`, `purgeOld`, `accOn`, `db.move`, the leader) is off, and `LOCK` stops every write, `db.save` and the fallback keys included (`db.save` answers `{ok:false, reason: save.reason.locked}` as under any lock). `writerLock()` is not asked for and `fbLocal()` does not run: **no note key** (`sheet:note:…`) is written, read keys stay byte for byte. Device settings in `sheet:settings` (`saveS`: the theme, the language, `current` when a note is clicked, `devId`/`devName` from `makeEngine()` when absent) may still be written, as under every other lock; they are not notes. After an `error` the background probe (§4.4) starts; after silence nothing more is sent, the hung request is the watch.
4. While the attempts run, nothing can change: the sheet is inert and the title not editable until `STARTED`, the list is empty, and a save that is asked for waits for the start (`tests/appformat.mjs` scenario 9, «a save made while the start still waits for the database waits too: it does not go to the fallback»). After 1 s of waiting the strip shows «Сховище браузера відкривається…» (`lock.opening`) with all four of its buttons hidden (`roRestore` and `roPurge` are visible in the markup and are only hidden by `roSync()`, which does not run before `db.init()` returns), so a slow or hanging open does not look like a frozen app; the start replaces it with the lock strip or hides it.

Typical cost: Chrome's `UnknownError` arrives as the request's `error` event after the backing-store attempt (tens to hundreds of milliseconds), so a device that recovers at the second attempt starts well under a second later than today and the user sees nothing. The worst case, two errors and then silence, locks the tab after about 9 s (0.3 + 0.9 s of waits, then the 8 s deadline); a hang at the first attempt locks it after 8 s.

### 4.2 What the view-only tab shows

- The notes `db.all()` finds in localStorage (`fbAll()`): the plain keys and the fallback copies left by writes that missed IndexedDB, with a differing older copy as «… (резервна копія)» in memory, exactly as the `other`/`nolock` locks show them today (`fbAll()`; the `newer` lock has the database and merges them with `fbMerge` instead). Usually there are none; then `newNote()` adds the empty note **in memory only** (`MEM`, never written: `newNote` already does this under `LOCK`), so the list and the sheet are not blank.
- The strip under the header, like the other locks (`roStrip`, `roMsg`, `roExport`, `roReload`): `lock.storage` «Сховище браузера не відкрилося, тож нотатки з цього пристрою зараз не прочитати. Оновіть сторінку; якщо не допоможе — закрийте застосунок і відкрийте знову.» with «Експорт» and «Оновити». The sheet is inert, the title fixed, the list items open notes read-only; «Нова», Ctrl+Alt+N and every other write say `lock.say` through `held()`; a paste on the sheet does nothing (its handler returns under `ro()` without a toast, as under every lock).
- The storage line replaces the count with a sentence: «Сховище браузера не відкрилося, нотатки пристрою не прочитані · експорт: …» (`storage.closed` in place of `storage.notes`): the count would be the empty in-memory note, which is not a note of the device.
- The account row and the status button are hidden, as under every lock (`accOn()` is false). The strip explains the state, so the hidden menu no longer looks like a sign-out.
- «Експорт» on the strip and in the gear menu export what is on the screen (`exportAll`: the in-memory notes, the empty `MEM` note left out, no `history` since there is no database). With no fallback copies the file has no notes; the button stays, since a copy may be there.
- «Оновити» reloads the page (`location.reload()`), which starts the retries again.
- `openNote()` does not save `current` for a note that lives only in memory (`MEM`: the empty note, a backup copy with a fresh id): it does not exist after the reload, and today it would overwrite the id of the real note the user had open, so the reload would land on `firstNote()`. A fallback copy keeps its own id and is saved as `current` as usual. This is a one-condition change in `openNote` (`if(!o.restore && !MEM.has(n.id)) saveS({current:n.id})`) and helps every lock, not only this one.

### 4.3 Edits, tabs, sync

- **Edits typed during the retries:** none are possible (§4.1, item 4). Tab messages that arrive before `STARTED` wait in `TABQ` as today.
- **Multiple tabs:** the locked tab holds no `baobook:writer` lock and no leader lock (`setLock` runs `leadOff()`; `leadAsk` is never called because the engine was not loaded from the store and has no owner). A second tab whose open succeeds works normally, moves the plain keys in under the writer lock and leads the sync. The locked tab keeps showing its in-memory copies until it is reloaded; `put`/`del` messages from the other tab reach it through `tabMsg` → `takeNote`/`dropNote`, which add to or leave the list under `LOCK` as the `other`/`nolock` locks do today (`dropNote` returns under `LOCK`). Two tabs that both fail are both view-only; no lock is needed, since neither writes.
- **The sync engine:** `SYNC=makeEngine()` is still made (it needs no store until `reload()`), `SYNC.reload()` and `db.move()` are skipped (`db.backend==='idb' && !LOCK` is false), so the engine has no owner and no queue and never steps. `accStart()` returns at `!accOn()`. Nothing is sent or received; the cloud is untouched. After a reload with the database open, everything resumes.
- **Writes that fail after a successful start** (`idbLost`, a transaction that fails, `DEBUG.failSave`): unchanged. `db.save` keeps writing the fallback copy `sheet:note:<id>~<tab>~<generation>` when IndexedDB refuses a write, and the copy moves in at the next start through `db.move()`; `unsaved`, «Повторити» and «Експортувати» work as today. Later opens (`idb.run`, `idb.tx`, `SDB.tx` after a closed connection) stay single attempts without a deadline: a retry there would only delay the fallback copy, which is the right outcome for a write.
- **The existing locks:** `newer` and `blocked` are decided inside the open and win over `storage` (`setLock` keeps the first kind). `updated` and `epoch` come after the start. `other` and `nolock` stay the locks of the fallback mode (no marker, or no `indexedDB` object); `storage` is the lock of a device that has the database but cannot open it.
- **The update strip (PR #91, `fix/stale-shell`):** `updCheck` runs regardless of `LOCK`; `updTry` waits for `updBusy()` only when `!LOCK`, so under the `storage` lock «Оновити» there reloads at once, which is also the recovery path. Both strips can show at the same time (one under the header, one above the toast). This PR raises `BUILD`, the meta tag and `build.json` as every change of `public/` does.

### 4.4 Recovery

- While `LOCK==='storage'` **after an `error`** (the queue is clear), `idbWatch()` probes the database in the background: 5 s after the lock, then 10, 20 and every 30 s, only while the tab is visible (`document.hidden` pauses the timer; `visibilitychange` to visible probes at once, which is how a phone brought back to the app recovers). A probe is a bare `indexedDB.open(IDB_NAME)` with a 3 s silence deadline, outside `idb.open` (it needs neither the `newer` check nor the `sync` read, and must not set `idb.db`); a `success` closes the connection at once and calls `idbBack()`; `error`, and a throw out of `indexedDB.open` (caught), count as «still closed» and the probing goes on; silence stops the probing (a silent probe is itself in the queue now, and a probe after it would queue behind it), and the silent probe becomes the watch like a silent attempt: its late `success` calls `idbBack()`, its late `error` clears `idb.silent` and schedules the next probe. `blocked` cannot fire on an open without a version; the handler is a defensive no-op.
- **After silence** (`idb.silent`) there is no probe: it would sit behind the hung request. The hung request itself is the watch: when the browser finally answers it, the dead attempt's `onsuccess` closes the connection and calls `idbBack()`; when it finally fails (`onerror` of the dead attempt), the queue is clear from that moment, so `idb.silent` is cleared and `idbWatch()` starts probing. Otherwise the recovery is «Оновити»: a reload starts a fresh request; whether it waits for the old one is up to the browser (in Chrome the hang is the backing-store open in the browser process), which is why the strip also says to close the app and open it again.
- `idbBack()` **reloads the page** (`location.reload()`): the tab is view-only and holds nothing unsaved (`beforeunload` asks nothing), so nothing is lost, and the reload keeps the open note when it is a real one (`tabCur`, `how==='reload'` in `start()`; §4.2 on `MEM` notes). The reload waits (and the probing continues) while an in-app dialog is open (`askDlg.open`, `choiceDlg.open`, `tszDlg.open`) or an export is in flight (`exportAll` sets `EXPORTING` around the download and the `navigator.share` sheet on touch devices), so it never closes something the user is reading or sharing. A lock → reload → lock loop is throttled: `sessionStorage` `sheet:idb-reloads` counts the automatic reloads, `db.init()` **clears it after a successful open** (a reload that landed in a healthy start is not part of a loop), and when it already reads 3 the strip changes to `lock.storageBack` «Сховище браузера знову доступне. Оновіть сторінку, щоб продовжити.» and waits for the button instead of reloading.
- A healthy device whose backing store takes longer than 8 s to come up (a cold start where the request waits behind the previous process's handles) is the silence case: the lock after 8 s, no probe, and the dead attempt's late `success` reloads the tab the moment the browser answers — self-healing, a few seconds slower than a start that succeeded at once (§9).
- The owner may prefer no automatic reload at all (§11, question 2); then every success changes the strip to `lock.storageBack` and the button reloads.

### 4.5 Devices that have never had IndexedDB

Unchanged: a browser without `indexedDB`, and a device without the marker (a fresh profile whose very first open fails, a private window in an old Safari), keep the fallback mode with the writer lock, the `other`/`nolock` locks and the plain keys. The retries run there too, so a fresh device that recovers at the second attempt starts normally.

### 4.6 Private mode, iOS and Safari

- The marker lives in the same storage partition as the database, so a private window (its own empty localStorage and IndexedDB) has no marker and behaves as a new device. Safari before 15 refused IndexedDB in private browsing: that is the no-marker path.
- Safari's hanging first open after a restore from the background is a silence failure: the tab locks after 8 s with the waiting strip shown from the first second, and recovers when the browser finally answers the request (`idbBack()`) or when the user taps «Оновити»; no probe runs behind a hung request (§4.4).
- iOS evicts the site data of an installed PWA that was not used for a while (ITP) — localStorage and IndexedDB together, so the marker goes with the database and the device starts fresh, as today.

## 5. Data

- One new optional key in `sheet:settings`: `idbOk` — the time in ms when IndexedDB first opened on this device, written by `db.init()` after a successful open when the key is absent (`saveS({idbOk:now()})`). Absent means «never». It is a device setting like `devId`: not exported, not imported, not synced.
- **Devices updated from the current code** have no `idbOk` at their first start with the new code. `S.versSwept` is written only by `vstart()` after the idle versions sweep ran with IndexedDB open (`db.backend==='idb' && !LOCK`; `vsweep()` catches its own errors, so the key proves the open, not a clean sweep), so `idbWorked()` is `!!(S.idbOk || S.versSwept)`: every device that has run the app with IndexedDB for one start of a few seconds is covered from the first start of the new code (`vstart()` runs from `requestIdleCallback(go,{timeout:3000})` and writes the key after the sweep, so a start closed within about 3 s leaves none; `idbOk` closes that gap from the first start on the new code). The reproduction in §2 shows `versSwept` set after the first normal start.
- No new store, no database version bump, no note field, no change to the export file. The LOCK kinds are a code constant, not stored.
- `sessionStorage` key `sheet:idb-reloads` (the count of automatic reloads of a lock → reload → lock loop in this tab, cleared by a successful open, §4.4), like `sheet:tab-current` and `sheet:signin`.

## 8. Tests

### 8.1 New scenario `tests/appidbfail.mjs`

Style as `tests/appformat.mjs` and `tests/appupdate.mjs`: one static server from `lib/server.mjs`, `CTX`, `ready`/`until` from `lib/wait.mjs`, `✓`/`✗` lines, exit code 1 on a failure, screenshots under `<tmpdir>/sheet-tests/`. An init script wraps `IDBFactory.prototype.open` and reads a mode from `localStorage.__idbfail` (per context) or `sessionStorage.__idbfail` (per tab, set after a first navigation to `blank.html` as `appformat` does): `''` passes through; `'error'` returns a plain object as the request and fires its `onerror` ~100 ms later with `error` = the `UnknownError` DOMException — Chrome's real shape, the `r.onerror` branch of `idb.open`; `'throw'` throws the same DOMException out of `open()` — the `catch(e)` branch of `go()`; `'once'` is `'error'` for one call and then clears itself; `'hang'` returns a request whose handlers are never called — it exercises the deadline code only, since a fake request does not enter the browser's real connection queue (a real hung request would also stall later opens, which no scenario can simulate); `sessionStorage.__idbpass` is a count of calls the wrapper lets through unchanged while a failing mode is set (for the probe of step 7). Every wrapped call appends `Date.now()` to `sessionStorage.__idbopens`, so the test reads the count **before** its own `indexedDB.open` calls and clears the mode before it seeds or reads the database itself. The marker `sheet:settings.idbOk` is read directly. The context puts `emulator:true` into `sheet:settings` before the first start, as `tests/emu/lib/app.mjs` does, so `FB` is set on `127.0.0.1` and the account UI is real (`accOn()`): the SDK loads only on a press, so no request leaves for a Google host. Before the lock the list is empty, so `ready()` (which waits for `#list .item`) is used only once the strip says `lock.storage`; the strip text is waited for with `until()` on `#roMsg`. Steps 2–4 and 7 run under `'error'` and are repeated under `'throw'`.

## 9. Risks

- **Latency on failure.** A silent request locks the tab after 8 s, two errors and then silence after ~9 s; the `lock.opening` strip after 1 s keeps it from looking frozen. A device where the open succeeds at the second attempt pays under a second once.
- **A healthy but slow device.** When the backing store takes longer than 8 s to come up (a cold start where the request waits behind the previous process's handles), the tab locks with the strip, and the moment the browser answers the still-queued request the dead attempt's `onsuccess` reloads the tab by itself (`idbBack()`): self-healing, with the lock strip shown for the seconds in between. No retry or probe is sent behind a silent request, since the IndexedDB connection queue would hold them until the hung one finishes (the round-2 finding, §12).
- **A request that fires `upgradeneeded` and never completes** (a hung upgrade transaction) keeps the start waiting forever, as today: the deadline is cleared by the first event on purpose, so a slow upgrade on a weak device is never cut short. Not seen in the wild; left as is.
- **A permanently broken database** (the open keeps failing on every start) leaves the device view-only with nothing to show, where today it at least lets the user write new notes into localStorage. This is the intended trade: the notes are in the database the user cannot see either way, and a silent second store next to them has caused the stray notes and the hidden account menu. The strip tells the user to reload and then to restart the app; the known last resort is clearing the site data by hand, which deletes the unreadable database (§10, item 8); an escape hatch into the fallback mode is §11, question 3.
- **The marker and existing devices.** `versSwept` as the legacy marker covers every device that has run `vstart()` once with IndexedDB. A device whose first start with IndexedDB is the first start of the new code and fails at that start takes the fallback path once, as today.
- **A dead attempt's late events.** Without the dead flag in every handler, a late `VersionError` would start a new open chain, a late `success` on an empty v1 would start an upgrade, and a late `success` reaching `done()` would overwrite `idb.db` of the live attempt and leave a stray connection that blocks a later upgrade by another tab. §4.1 and §6 make the flag the first check in `go()`, `onsuccess`, `onerror` and `onblocked`; a late `success` closes its connection at once.
- **Automatic reload loops** are bounded by the counter (§4.4); a reload never interrupts a dialog or an export in flight.
- **`UnknownError` on a transaction instead of the open** (a database that opens but refuses to read) is not covered: `db.all()` then falls back to `fbAll()` as today with `db.backend==='idb'`, and the start shows the copies with the account menu on. Watching for it is a manual check (§10); a fix would be a `storage` lock on a failed first read, out of this PR.
- **The `blocked` interplay**: a tab blocked by another tab's old connection still becomes `blocked` after 3 s, not `storage`, since `setLock` keeps the first kind and `idbOpenRetry` stops when `LOCK` is set.
