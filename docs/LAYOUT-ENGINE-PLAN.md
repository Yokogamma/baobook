# The layout engine: implementation plan

**Status: after review round 4 (2026-11-03), two checks of the owner's decisions of 2026-11-04, the independent review of 2026-11-04 (1 blocker and 6 major findings, all fixed the same day, with S8's way chosen by the owner in the mockup), and the architecture review of 2026-11-04 (14 findings, accepted in full by the owner with R1, rules that switch), after which the plan was restructured (review log): ready to start step 1.** This plan builds the engine that [`LAYOUT-RULES.md`](LAYOUT-RULES.md) specifies and puts it into the current app as version 0.1. It answers E-5 of that document (the steps of `LAYOUT-MODEL.md` §7, re-planned for the decided model) and settles E-1 to E-4 for 0.1. Where this plan and `LAYOUT-MODEL.md` §5–§7 disagree, this plan wins; those sections described the anchor-and-sweep model that G1 replaced.

Rules are cited by their ids in `LAYOUT-RULES.md` (`SIZE.1`, `P-ASIDE`, `INV-8`…), the switches by the ids of its §1.6 (`GAP.5.1`, `THROUGH`…); decisions by their ids in the table of `LAYOUT-MODEL.md` §2 (`W3`, `G6`…). **(proposed)** marks what rests on no decision of the owner yet.

## 1. What version 0.1 is

The engine takes over **placement only**: where every block stands, how wide and tall it is shown, and what happens to the other blocks when one is carried, resized, created, deleted, grows or shrinks, or goes into or out of an area. Everything else stays as it is in `public/index.html` and is not rewritten: the blocks' DOM and their content, typing and formatting, links and chips, the commands of the block menu (copy, delete, convert, colour, «Копіювати посилання»), the structural undo stack, history, trash, sync, tabs, import and export. Those features keep their code; where they change the layout today they call the engine instead of today's layout functions (§6).

Four properties make 0.1 a safe first release:

1. **No change of the stored format** (§3). A note written by 0.1 is read by the current version on `.app` as a valid note, and the other way round. No migration, no `FORMAT` raise, no new Firestore rules.
2. **A switch.** Until step 6 the engine is off by default and is turned on in the settings menu for testing on `.dev` («Нова розкладка (0.1)», a device setting in `sheet:settings`, its label in `uk.json` and `en.json`). A tab reads it once, when it starts; changing it reloads the tab, so a tab never runs both layouts. Off, the app behaves exactly as now.
3. **Pure core.** The rules run in Node without a browser, with a stub for measuring text (§4.3), so every rule of `LAYOUT-RULES.md` has fast tests before anything is wired.
4. **Rules that switch** (R1). Every rule that is not core can be turned off without breaking the others: the engine takes the set of rules as an input (`rules`, §2.1), a rule turned off gives way to its fallback, and the rules that need it go off with it (`LAYOUT-RULES.md` §1.6). Every rule is on by default. On `.dev` a «Правила» list in the testing look's settings turns them on and off (VIEW.8), a device setting in `sheet:settings` that no note stores, so the owner can try combinations on real notes and a rule that misbehaves can be told from the others. Every test of a switchable rule runs with it on and off (§5).

## 2. The modules

`public/layout/`, wired like `public/account/`: ES modules, each file a row of the `SRI` table in `index.html` (809), which also puts it into the import map through `MODS` (815–817), and, from step 5, an entry of `PRECACHE` in `sw.js` (18), as the account files are; `tests/hashes.mjs` finds every `public/<feature>/*.js` by itself (§5). The `model` role is split by the modules of `LAYOUT-RULES.md`, so a rule lives in the file of its module. No file reads a global; every shape is described once, in `shapes.js`.

The passports of `kinds.js` reach them only as `ctx.kinds` (§2.1). `drag.js`'s target functions and every `ops.js` action take `ctx`, as `settle` does. `view.js` and `input.js` receive the bridge and the measuring function as arguments, and `ctx` (the rules and the settings) from the bridge beside it; `panel.js` receives the bridge and `ctx`; all three read `ctx` again when the «Правила» list changes.

### 2.1 The engine's surface

```js
/** The stored state of one container and its derived rows. The bridge builds the Boxes from index.html's blocks with `w` and `h`
 *  unset and no gaps or lends; `open()` sizes them and finds the pairs.
 * @typedef {{id:string, kind:string, col:number, y:number, w?:number, h?:number, cw?:number, ch?:number, open?:boolean, collapsed?:boolean,
 *            above?:Map<string,Run[]>, lend?:Map<string,Run[]>}} Box
 *   // above: the gap over this block from each of its upper neighbours, keyed by the upper block's id; empty for a head block
 *   // lend: the rows its body covers in the gap of a pair it stands between, one per pair, keyed 'upper>lower' ('>lower' above a head block)
 * @typedef {{o:?string, n:number}} Run                      // n rows owned by block o, or unowned (o null)
 * @typedef {{cols:number, boxes:Map<string,Box>, areas:Map<string,Layout>}} Layout   // no pairs of its own: they are its boxes' `above`
 * @typedef {{col:number, y:number, frow:number, w:number}} Target   // a moved block's cell, its unrounded row and its width at the target
 *   // the state of LAYOUT-RULES §1.4 («move», «home», «outside») stays in drag.js: at «home» or «outside» no change is made (PR-1), so SETTLE never sees it
 */

/** The switches (R1, LAYOUT-RULES §1.6) and the settings: the engine's input besides the layout, the change and the memory.
 * @typedef {'SIZE.1'|'SIZE.2'|'SIZE.8'|'GAP.2'|'GAP.5.1'|'GAP.5.2'|'GAP.5.3'|'GAP.8'|'P-ASIDE'|'P-UP'|'P-REST'|'P-SINK'|'THROUGH'
 *          |'DRAG.A2'|'DRAG.A3.narrow'|'DRAG.A4'|'DRAG.A5'|'DRAG.B1'|'DRAG.B2.keep'|'DRAG.B3'|'DRAG.B5'|'DRAG.C4'|'RESIZE.1'|'RESIZE.2'|'RESIZE.3'
 *          |'AREA.3'|'AREA.6'|'AREA.7'|'AREA.7b'|'EDIT.3'|'EDIT.4'|'VIEW.1.fit'|'VIEW.1b'|'VIEW.2'|'VIEW.6'} RuleId
 *   // 35 ids, one per 0.1 row of LAYOUT-RULES §1.6; 0.2's (SIZE.7, P-SQUEEZE, AREA.4, AREA.8) join with their rules
 * @typedef {{id:RuleId, needs:RuleId[], fallback:string}} RuleDecl   // fallback: the name §1.6 gives what runs in its place, for the tests; the list's words are in uk.json and en.json
 * @typedef {Readonly<Record<RuleId, boolean>>} Rules             // every RuleId present, closed over the needs; made only by resolve()
 * @typedef {{TEXTW:number, MINC:number, ORDER:'push'|'never', STICK:number, NEAR:number, HOLD:number, STILL:number, MINSCALE:number, RESTPASSES:number}} Settings
 *   // LAYOUT-RULES §1.5; at their defaults in 0.1. FOLDPHONE is view.js's: it only feeds `temp` for `show` in the narrow view (VIEW.2);
 *   // PASTEFOLD and DESKW are 0.2's
 * @typedef {{rules:Rules, settings:Settings, kinds:Record<string,Kind>, measure:Measure}} Ctx
 */
export function resolve(partial)   // {[RuleId]: boolean}, ids left out on → Rules: every rule whose needs are not all on turned off, transitively; pure (rules.js)

/** What a step moved, for GAP.5 rule 1: phase 1c, phase 3's pin and swap, and every primitive return the edges they moved, and SETTLE
 *  accumulates them per block id for the RELINK they are handed to («Inside `settle`», below). A block that follows a step with its gaps
 *  is moved by that step. A row FOLLOW changed after a height and a bottom that the block's own height changed are never in it.
 * @typedef {{step:number, by:'change'|'swap'|'aside'|'up'|'down'|'sink'|'sep'|'rest', rows:number}} Step   // step: a counter, one per call of a primitive in this SETTLE; rows: down positive
 * @typedef {{top:Step[], bottom:Step[]}} Moved   // every step that moved the block's top and its bottom, in order; rule 1 takes out the rows both edges of a pair were moved by the same `step`
 */

/** One per row of LAYOUT-RULES §5.2 «Change kinds», as data in changes.js, keyed by Change.type; settle.js reads it.
 * @typedef {{moved:'none'|'target'|'targetAway'|'self', judge:'carry'|'wall'|'none', noRoom:'side'|'sink'|'none',
 *            contain:{width:'clamp'|'none', bottom:'grow'|'refuse'|'none'}, memory:'carry'|'gestureStart'|'none', phases:number[]}} ChangeKind
 *  moved: a moved block put at its target in phase 1c ('target': a carry, and an arrow, whose «away» is DRAG.B1's for its one target), or put
 *  there away from the start ('targetAway', for `create`, the second settle of an enter or a leave included, DRAG.B1), the block itself at its
 *  new width, and for an area's left edge at its new column ('self', the width handle and an area's side), or none; the carry's judge reads «away» from the kind when the memory is 'none';
 *  judge: phase 2 by DRAG.B2 and B3 ('carry'), by the wall's judge, for an area's side handle and for the width handle's right edge ('wall'),
 *  or nothing;
 *  noRoom: what a block P-ASIDE put back does, by its side (DRAG.B5), by `sink` (P-SINK), or nothing; a refusal is not a kind's `noRoom` value
 *  but the fallback rules.js names for DRAG.B5 and P-SINK off;
 *  contain: phase 10, per edge: a carry, an arrow and a new block {width:'clamp', bottom:'grow'}: DRAG.A3's rule, which a carried target
 *  already obeys and a created one (a paste, «блок після», a `set.cw`) gets here;
 *  the width handle {width:'clamp', bottom:'grow'}; the wall and (0.2) the area's top or bottom handle {width:'none', bottom:'refuse'};
 *  a size {width:'none', bottom:'grow'}; a deletion {width:'none', bottom:'none'};
 *  memory: the carry memory, the gesture's start (RESIZE.1, AREA.6), or none, a size's included (EDIT.6 is EDIT's own memory);
 *  phases: a list of phase numbers: the carry's 1–11 (3 and 11 act with THROUGH on), the arrow's, the new block's and the width handle's
 *  1, 2, 4–10; phase 1 runs its sub-steps by the change: 1a on sizes it sets, 1b on a removal or an away block, 1c on a `moved` other than 'none' */

/** One typedef per kind; `box` is the container the change is in (null, the sheet).
 * @typedef {{type:'carry', box:?string, id:string, at:Target, through?:'hold'|'shift'}} CarryChange   // a pointer move; through: set by input.js when its hold timer ran out against `pressed`, or Shift is down (DRAG.B4); phase 11 chooses only then
 * @typedef {{type:'arrow', box:?string, id:string, at:Target}} ArrowChange             // the cell the jump aims at, a carry dropped at once (DRAG.C4)
 * @typedef {{type:'create', box:?string, id:string, kind:string, at:Target, set?:{cw?:number, ch?:number}}} CreateChange   // a click, «+», a paste, «блок після», a block made on a narrow screen, an area drawn
 * @typedef {{type:'width', box:?string, id:string, cw:number, side?:'left'|'right', col?:number, rows?:number}} WidthChange   // the width handle (right); and, from areaSide, an area in its container: col its new column for the left edge, rows its new height from the area's settle
 * @typedef {{type:'wall', box:string, side:'left'|'right', cols:number, shift?:number}} WallChange   // an area's side handle inside the area (from areaSide): its new columns; shift: for the left edge, the columns every child moves by to keep its cell on the sheet (AREA.5)
 * @typedef {{type:'areaSide', box:?string, id:string, side:'left'|'right', col:number, cols:number}} AreaSideChange   // the area `id` in the container `box`: its new outer column and width, clamped to the container before either part runs
 * @typedef {{type:'size', box:?string, id:string, set?:{cw?:null, ch?:?number, open?:boolean, collapsed?:boolean}}} SizeChange   // typing, a re-measure, the height handle, a fold, a collapse, an area grown (settleTree)
 *   // cw null: the width handle's double click, RESIZE.2, a size change (LAYOUT-RULES §5.2)
 * @typedef {{type:'remove', box:?string, id:string}} RemoveChange
 * @typedef {{type:'enter', box:?string, id:string, to:string, at:Target}} EnterChange   // into the area `to`: a removal in `box`, then a new block in `to`
 * @typedef {{type:'leave', box:string, id:string, to:?string, at:Target}} LeaveChange   // out to the container `to`, the same two settles
 * @typedef {{type:'ungroup', box:?string, id:string}} UngroupChange                    // the area `id` taken away, its children put on its cells
 * @typedef {{type:'drawArea', box:null, id:string, at:{col:number, y:number, cols:number, rows:number}}} DrawAreaChange   // AREA.7b
 * @typedef {CarryChange|ArrowChange|CreateChange|WidthChange|WallChange|SizeChange|RemoveChange|EnterChange|LeaveChange|UngroupChange|AreaSideChange|DrawAreaChange} Change
 *  enter, leave, ungroup, drawArea and areaSide are composite: settleTree takes them apart (LAYOUT-RULES §5.6), and only the parts reach settle
 *  and the ChangeKind table: remove and create changes; drawArea a create of kind 'area' with its rows (`set`); areaSide a WallChange in the
 *  area and then a WidthChange of the area, with its new height, in its container, accepted or refused together, both containers in `ran`
 */

/** What a block cannot pass, for P-ASIDE, `sink` and P-UP: a wall, a container's edge, a block that cannot move.
 * @typedef {{cols:[number,number], rows:[number,number], pushes:'left'|'right'|'none'}} Obstacle   // its first and last column and row; pushes: the side a wall presses to
 */
export function isHead(box)                                // no upper neighbour (`above` empty): its stored row is trusted (gap.js); every primitive and INV-2 ask it
export function canMove(box, dir)                          // 'left'|'right'|'up'|'down'; in 0.1 every block can, within its container (primitives.js)

/** The carry memory (LAYOUT-RULES §6.D): only what SETTLE reads, with `start`, which `settle` takes and returns beside it.
 *  DRAG keeps the start place and pointer for DRAG.A2 and A4, input.js the hold point and timer, view.js the note's width frozen for the carry.
 * @typedef {{away:boolean, sides:Map<string,'left'|'right'>, through:?{id:string, row:number, side:'below'|'above'}, areaBottoms:Map<string,number>, lastTarget:?Target, dir:'up'|'down'}} Memory   // dir: the last vertical direction (LAYOUT-RULES §6.D), down at first, changed only when the target row changes (settle compares at.y with lastTarget.y before phase 2), so a hold or Shift after a pause or a sideways move still knows it
 */
export function settle(start, change, memory, ctx)         // in one container, on the displayed layout → {layout, start, memory, pressed, moves, grew}, or {refused},
                                                           //   or {failed} (LAYOUT-RULES §5, §5.5); moves: Map<id, Moved>, the union of every RELINK's (below);
                                                           //   grew: the difference between the area's shown height in the result and in `start`, in rows, negative when it shrank
export function settleTree(root, change, memory, ctx)      // the sheet and its areas (LAYOUT-RULES §5.6) → {layout, start, memory, pressed, ran}, or {refused}, or {failed};
                                                           //   ran: the containers it settled; it settles a container's parent while `grew` is not 0
export function relink(base, after, moves, carried, rules) // GAP.5 in one container → `after` with the `above` and `lend` of its blocks set (gap.js)
export function open(stored, ctx)                          // a Layout of Boxes from the bridge (no gaps, sizes unset) → {layout}, or {failed, layout}: §3.5; writes and records nothing
export function show(canonical, temp, ctx)                 // the displayed layout: FOLLOW with the displayed measure, ctx.measure with the rows of `temp` per block id (LAYOUT-RULES §2.1)
export function unshow(displayed, ctx)                     // the canonical layout: FOLLOW with the canonical measure, ctx.measure
export function diff(stored, after)                        // the stored fields of `after`'s blocks that differ from `stored`, the fields as the bridge read them (§3.4), per block id
```

**One layout, two measures** (`LAYOUT-RULES.md` §2.1). The canonical measure answers every block's rows with no temporary height, the displayed measure with them; `show` is FOLLOW with the displayed measure and `unshow` FOLLOW with the canonical one, so the two layouts have the same pairs, gaps, lends, widths and head rows. Every action runs `settleTree` on the displayed layout, `show(current, temp, ctx)`, with the displayed measure in its `ctx`; the result is drawn as it is, and its canonical layout, `unshow(result, ctx)`, is what `diff` compares, what the undo entry keeps and what the next action starts from.

**Inside `settle`.** The pipeline is phases 1–10 (`LAYOUT-RULES.md` §5.1), run in order every time; phase 3, the pin and the swap, acts only for a carry with `THROUGH` on, after 1c and 2. The THROUGH wrapper is phase 11 and the runs again (§5.1b): after a choice in phase 11 or a swap in phase 3 it runs phases 1–10 again, phase 3 included, within the bounds of §4.2; nothing inside the pipeline starts it again. Phase 2 asks the change kind's judge, a block P-ASIDE put back goes to the kind's no-room branch, and phase 10 contains by the kind, so `settle.js` holds no table of changes. Phase 1c, phase 3's pin and swap, and every primitive return the edges they moved, and `settle` hands them to `relink` as `moves`. `moves` is relative to the `base` of the RELINK it is handed to, and every RELINK empties it: a swap's RELINK in phase 3 gets the moves of 1c, the pin and the swap, and the swap ends that run, the run again starting from the swapped layout as `start`, whose phase 1 makes a new `base`; phase 8 gets the moves of phases 1c–7; phase 9 (c) gets only phase 9 (b)'s (`by: 'rest'`); the `moves` that `settle` returns is the union, for the dev look. `settle` stays local to one container; `settleTree` drives the containers: it settles the change's container, and while a result reports a `grew` other than 0, settles that container's parent with a size change of the area, so the blocks under an area that shrank come back by the same path as those under one that grew; an enter or a leave is two settles in order, a removal in the container left and a new block in the one entered; an area's side handle is two too, the wall in the area and then the area's width change, with its new height, in its container, accepted or refused together (`LAYOUT-RULES.md` §5.6).

**Three results.** `settle` and `settleTree` return a result, `{refused}` or `{failed}`. `{refused}` is returned when the change kind's containment refuses (`bottom: 'refuse'`) or a switched-off rule's fallback is «refused» (`DRAG.B5` off, `P-SINK` off): it writes nothing and it is not a bug; the caller keeps its last accepted result, so a carry stays at its last accepted target and a handle stands at the nearest accepted rectangle (`LAYOUT-RULES.md` §5.4). `{failed}` stays the bug result (§4.2).

**The `rules` input.** The bridge resolves the device setting of VIEW.8 when a note opens and passes the same `Rules` in `ctx` to every call until the setting changes; on `.app`, with no list, they are `DEFAULT`. Every module that owns a switch reads it from `ctx.rules` and nothing else reads a switch: a phase whose rule is off is skipped or runs the branch its fallback names, and each GAP operation reads the one switch it owns (§1.6). `Settings` are the parameters of their rules, at the defaults of §1.5 in 0.1.

**Where the gaps live.** A gap is kept on its lower block (`above`, keyed by the upper block's id) and a lend on the block whose body covers it (`lend`, keyed by its pair), so every fact about a pair belongs to one block, as sync merges a note by block and by group of fields. `Layout` holds no pairs; a module that visits them in order builds an index from the boxes, never kept. 0.1 stores neither (§3.3). In 0.2, when they are stored, `above` and `lend` join the block's place group in sync (`sync.js` 103), and the conflict test should leave out the rows of blocks that are not head blocks, which are derived (`LAYOUT-RULES.md` §2.1).

`ops.js` builds on `settleTree` one function per action of §5.2 (`drop`, `arrow`, `create`, `remove`, `grow`, `width`, `height`, `areaSide`, `areaBottom`, `enter`, `leave`, `ungroup`, `drawArea`); `width` makes a width change for the handle and a size change with `cw: null` for its double click (RESIZE.2); `input.js` calls them; the bridge writes what `diff` returns and pushes one undo entry.

## 3. Data in 0.1

### 3.1 Columns

The engine's `col` is the handle cell; the card starts at `col + 1` (`LAYOUT-RULES.md` §1.1). Today's code keeps a different number:

- **In an area** a child stores `col`; its grip stands in the area's cell `col` and its card starts at cell `col + 1` (`xlOf` with `cOX(area) = APAD`, `index.html` 2328–2336). The engine's `col` is the stored `col`.
- **On the sheet** a block stores `fx`, the left edge of its *text* as a share of the sheet's width in pixels: `fx = xOf(c) / W()`, with `xOf(c) = G/2 + c × G` and `c ≥ 1` (`cMinCol`). The card starts on the dot column `c`. The engine's `col` is `c − 1`.

In 0.1 nothing new is stored. The sheet is read at one fixed pixel width `W0px` instead of the window's:

- **Read:** `c = round((fx × W0px − G/2) / G)` with `G = 24` whatever the text size, and no clamp here (today's `colOfX` clamps by pixels, `maxColFor`; §3.5 is the engine's only edge); the engine's `col = c − 1`. `SHEETW` is the number of columns today's dot grid shows at that width, `floor((W0px − 2.5 × 24) / 24) + 1` (`field()`, 2398), the same for every note in 0.1.
- **Write:** a sheet block whose column a user action writes (§3.4), because it differs from the column read, gets `fx = (G/2 + c × G) / W0px` with `c = col + 1` and `G = 24`. Reading that back gives the same `c`, so the mapping is exact both ways; a block whose column is the one read keeps its stored `fx` untouched. Step 1 pins both with a round-trip test through `serBlock` and step 5 with a scenario that saves an unmoved note and compares the bytes.
- **The current version** reads the same `fx` at its own `W()` and clamps it to its `maxColFor`, on every resize of its window (`applyMode`, 3125), as it does today.
- **Exact at the default text size only.** Today's code writes and reads `fx` with the cell of the current text size, so a note edited at a larger text size reads to other columns at `G = 24`, and a current-version tab at a larger text size reads the engine's `fx` to other columns (§1.3, §7).
- **`W0px`** is a question for the owner (`LAYOUT-MODEL.md` §9): the width in pixels of their sheet (`sheet.clientWidth`) on their usual computer, with the list of notes open, at the default text size; most of their `fx` were written at it, and an error of half a cell moves a block on the right by a column. The owner measured 1451–1466 px on both computers they use, a 14-inch laptop and a 24-inch display (2026-11-04, W11): a window with and without the vertical scrollbar, so notes were written at both. `W0px` is their middle, 1458 px: a block written at either width reads back to its own column, the error staying under 8 px of a 24 px cell. `SHEETW` is then 59 columns.

**Rows.** In an area the engine's `y` is the stored `row`. On the sheet it is `row − 2`: a sheet block's first row today is 2 (`cMinRow`, 2334; `clampRowFor`), the rows above it left empty, so that row is the engine's row 0; a write stores `row = y + 2`.

**Children and the sheet.** An area is a Box at sheet `(a, y)` with `H` header rows (`container.headerRows`); its child at `(c, r)` stands on sheet cell `(a + 1 + c, y + H + r)`, its handle on the area's column `c`. This is `LAYOUT-MODEL.md` §3.1's mapping in the engine's columns. `enter` and `ungroup` use it, and «З області» (`leave`) its column part, since AREA.7 puts the block under the area in the column it had inside; `ops.js` works in cells only.

A note's sheet is `SHEETW` columns on every device. Its scale is fitted to the width the note uses, up to its rightmost block (W12): a window at least that wide shows it at full size, white room to the right when it is wider than the sheet, the rest of the sheet reached by the sideways scroll when it is narrower; a narrower window scales the note down to `MINSCALE`, narrower still the narrow view (VIEW.1, VIEW.2). The user may zoom in with «+» and move with the hand. The fitted scale is recomputed on opening and after an action, never while typing, only when the caret leaves the block; carried to the window's edge, a block makes the sheet scroll by itself (W16).

### 3.2 Sizes

- **`cw`** is the set width (SIZE.3) for texts and code; an area's `cw` is its width.
- **`ch`** of a text is its set height, spare room below the text (RESIZE.3); 0.1 writes only `ch`.
- **Code** keeps its fields: its `ch` is its fold height and `open` the user's choice of the full height, as today (`LAYOUT-MODEL.md` §5). The engine reads its shown height and its width from the passport (§4.4).
- **Areas** keep `ch` (a set height, AREA.2) and `collapsed`; with no `ch` an area is as tall as its blocks need, so it shrinks when they do (A3). A collapsed area shows its header only; its children keep their stored places and take part in nothing until it is opened. A carried block does not enter a collapsed area: its frame is an edge as AREA.7a says (proposed, until folding comes as one function in a later release, A3; today a collapsed area is pushed, an open one entered).

### 3.3 Pairs and gaps (E-1 for 0.1)

0.1 stores no pairs, gaps or lends. `open()` finds every pair from the places with every pair fresh (GAP.5 rule 4, `fresh`: the rows belong to the block above) and the engine keeps them in memory with the open note, each gap on its lower block's `above` and each lend on the block that covers it (§2.1); every rule runs on them as written, and every user action writes the places that result (§3.4).

The memory lasts while the note is open in the tab and nothing replaces its stored places from outside. It is found again by `open()`, with every gap belonging to the block above it, after a reload, after a change from another tab or device (`safePoint`, `takeStored`, `takeNote`), after an import, after restoring a version and after a change of the «Правила» list (VIEW.8). An undo keeps it (§6.4). Leaving the view of an old version («Історія») puts back the layout and pairs the bridge kept aside (§6.1). So INV-7 holds within one open note between such events, and across them a gap is never lost, it only changes hands; 0.2 stores the pairs and lifts this.

### 3.4 Rows and what a user action writes

A user action writes, through the bridge, in every container its `settleTree` ran in, the stored fields of the blocks whose canonical place or set size differs from what is stored, as the bridge read it (§3.5): rows and columns, `cw`, `ch` (`diff`, §2.1; the canonical layout, `LAYOUT-RULES.md` §2.1). That covers three things at once, with no bookkeeping:

- what the action moved or resized;
- what FOLLOW moved under a text that grew or shrank, as today's `relayout` does, the derived rows written as caches (`LAYOUT-RULES.md` §2.1);
- what changed earlier with no user action and was only shown: the places `open()` repaired, clamped, separated or re-rested (§3.5), and the places a re-measure no user made moved, a linked note renamed, which changes a chip's label, or a font that loaded after the note opened (§4.3). The user has seen them, and writing them keeps the layout the same after a reload and for the current version. They include separations that come from this device measuring a text taller than the device that wrote the note: `open()` cannot tell the two causes apart (§7).

Nothing records which blocks are in the third group: they differ from the stored fields until an action in their container writes them, and an undo that puts the stored fields back makes them differ again, so the next action there writes them again. In 0.1 every stored row is a place for `open()`, since no pairs are stored to derive rows from; the rule that only head blocks' rows are trusted applies from 0.2. A temporary height is shown and never written, and neither is a row it moves, since the canonical layout has neither: the field row of wide fields (P18) is one. Nothing is written with no user action: opening a note, a view-only re-measure, a change of the «Правила» list (VIEW.8) and applying a change that came from another tab or device write nothing by themselves.

What this saves against today: opening a note writes nothing, and a keystroke that changes no height writes no row in a container whose stored places are the ones shown; a device that measures differently writes its own separations once, with its next action in that container, and otherwise only the blocks an action moves. `row` is in the sync «place» group (`sync.js` 103), and a place group changed on two devices makes a conflict copy.

### 3.5 Opening a note

Every note on `.app` was laid out by today's `resolveIn`, whose result depends on the window's width and the order of the stored array (`LAYOUT-MODEL.md` F1, F4–F6). Read at `W0px`, its places may break the invariants: two cards overlap, a block lies past `SHEETW`, a child lies outside its area, a block stands in the free cell round an area (AREA.7a). `open()` makes a valid layout of them, shown and not written.

**Reading.** The bridge reads the stored blocks as `make` and `makeAll` read them today (2099, 2401–2408), so a note shows the same blocks: areas first; a text with no content is not shown, as today; an area has no parent (no nesting); a block whose parent is not an area of the note stands on the sheet, its column from its `col`, as `make` does, or from its `fx`. Every value `normBlock` accepts (`sync.js` 54–68) gives a place: a fractional `col`, row or column read from `fx` is rounded to the nearest cell, and the engine's `col` and `y`, after the offsets of §3.1, are at least 0 (today `clampRowFor` keeps a sheet row at `cMinRow`, 2, or more); `cw` and `ch` are read rounded up to whole cells and at least the kind's minimum. The bridge keeps every block's stored fields as read, for `diff` (§3.4): a sheet column as §3.1 rounds it from `fx`, any other place as stored, fractional or negative, and `cw` and `ch` as read here. So a repair that changes a place differs from what is kept and is written with the next action in that container, and no repair writes `cw` or `ch`; the bridge updates what it keeps with every write of its own, and with the fields an undo puts back. Before anything else every value is checked against the engine's range (`MAXCELL`, `LAYOUT-RULES.md` §1.5): `normBlock` accepts any finite number, so a `row` of `1e20` or a `ch` of `1e308` is a valid stored note, but not a place the engine can compute with. A note with any column, row, width or height that, after the conversions of §3.1, is not a whole number from 0 to `MAXCELL`, opens in the safe mode below: each value shown clamped into the range, placement off, nothing written, the stored values untouched; the strip says that the layout of this note is not supported. The range is the engine's, not the format's: `sync.js` stays as it is.

0. **Sizes.** Every block's width and rows at its stored place: `RESTPASSES` passes of SIZE.8.
1. **Clamp.** A card past its container's right edge moves left to the last column where it fits; an elastic block narrows first, as at the edge (DRAG.A3). A set width wider than its container (an imported note, a `cw` written on a wider window or in a wider area: `normBlock` accepts any positive `cw`, `cw: 80` on a sheet of 59 columns) is shown at the container's full width, from its column 0, as today's `render` caps it at the room it has (2362); its `cw` stays as stored, and is written only when the user sets a width with the handle. SIZE.3 still holds: no rule narrows that block, it is only shown inside its container. An area wider than the sheet is shown the same way, its children laid out in the width shown. A child below its area's set height makes the area taller in the layout (AREA.2).
2. **Separate.** As today's `resolveIn` does: keep a list of placed blocks, empty at first; visit the blocks in reading order of the layout as it stands, ties by id; a block that hits a placed one, or stands in the free cell round an area, goes down alone to the bottom of the block it hits (or below the area's free cell), and is placed; when a pass moved a block, visit again from the start in the updated reading order; stop after a pass that moves nothing. Rows only grow and a placed block never moves, so this ends. It is P-SEP between two uncarried blocks (S6), done before any pair exists.
3. **Pairs.** RELINK with every pair fresh and no `moves` (§3.3).
4. **Rest.** Phase 9 of SETTLE at rest: `RESTPASSES` passes of SIZE.8 on the separated places, so a text that a moved neighbour no longer presses widens again and a block that came down beside a text narrows it; FOLLOW; P-REST and P-SEP for any hit this leaves; RELINK. This is what `resolveIn` does today by measuring again between its passes.

5. **Temporary heights.** Only now is the displayed layout made (`show` with the displayed measure, `LAYOUT-RULES.md` §2.1): «Розгорнути», a code block unfolded while it is edited, the wide field row of P18. Every SETTLE runs on the displayed layout, while `diff`, the undo and the next action keep the canonical one, so none of them is ever written.

Every step runs under `ctx.rules`, so a rule turned off in the «Правила» list changes what `open()` shows (VIEW.8). `open()` records nothing of what it moved: what the reading and steps 1, 2 and 4 changed differs from the fields the bridge kept, and that is all §3.4 needs.

**If `open()` fails, and the safe mode.** The reading and the steps above give a layout for every note `normBlocks` accepts whose values are in the engine's range; only a bug can exceed a bound inside them (§4.2). The bridge checks the range before it calls `open()`; a note out of it never enters it, and the bridge builds the safe layout itself, as below. Such a note can be repaired only by changing its stored values (an export edited and imported), since placement is off in it. Then `open()` returns `{failed, layout}`, every block at its read place and size and nothing separated. The bridge shows that layout, turns placement off for that note in this tab (no carry, handle, arrow, area gesture or creation on the sheet; typing and the commands that are not placement stay, and a height change moves nothing, so blocks may overlap as shown), writes no place and no size for it, and says so in a strip with its own key in `uk.json` and `en.json`; the dev look reports the case. Its text is saved as any edit is, through the normal guarded pipeline (the owner, 2026-11-04): what is never written is a place or a size, so the stored geometry stays exactly as it was, unclamped, and the safe display never becomes the source of a placement write. The next start tries again.

The result is the layout the next action starts from; what the reading and steps 1–4 changed is shown and not written until the first user action in its container writes it (§3.4). `open()` is deterministic: the same stored note gives the same layout on every device that measures the same. The current version keeps writing its own pushes until 0.1 reaches every device (§7); `open()` reads them as places like any other.

## 4. Engineering points settled for 0.1

### 4.1 Determinism (INV-5)

Every visit is in reading order of the layout its phase starts from, ties by id, the ids compared by their code units (`a < b`), never by `localeCompare`, whose order follows the device's language; nothing depends on the order of the stored array (`LAYOUT-MODEL.md` F4). Measured sizes may differ between devices with different fonts; the stored rows are each device's own result of a user action, every stored row is a place for `open()` in 0.1, and what a device separates or re-rests because it measures differently is written only as §3.4 says.

### 4.2 Bounds (E-2)

- `RESTPASSES` is 2 (proposed): two passes of SIZE.8 in phase 9 (a). The reference in the tests runs passes until two in a row give the same layout, or as many passes as the container has blocks; a case where two passes differ from it, or that reaches that count (a cycle), becomes a regression test, and the number is raised or the rule fixed.
- Phase 9 (b) ends because each step moves a block right within the container or down, and narrows elastic blocks only, so the sum of the blocks' columns and rows rises at every step and has a ceiling. `RESTSTEPS` (`LAYOUT-RULES.md` §1.5, §5.1) is the guard on it, not that ceiling: the container's blocks × its `cols` × 4, known before anything is measured, so counting the steps costs nothing; a sequence that reaches it is a bug. `open()`'s separation (§3.5 step 2) only moves blocks down, a placed one never, within the engine's range (`MAXCELL`), so it ends too; it is guarded like phase 9 (b), at most as many passes as the container has blocks, plus one, and more is a failure (§3.5).
- Runs of the pipeline: the THROUGH wrapper (`LAYOUT-RULES.md` §5.1b) runs phases 1–10 again, phase 3 included, within one pointer move, at most once for every neighbour swapped in that move (phase 3) and once after a choice (phase 11); the count starts again at every move, so a swap and a swap back over several moves are allowed; nothing inside the pipeline starts it again. `settleTree` settles one container more for each area whose shown height changes on the way up (`grew` not 0), at most the depth of areas (one level in 0.1), and one more for the second container of an enter, a leave or an area's side handle.
- A bound exceeded is a bug: `settle` returns `{failed}` (`LAYOUT-RULES.md` §5.5), so the action writes nothing and a gesture ends as a cancel; `open()` returns `{failed, layout}` (§3.5). The dev look reports both with the change and the layout, for a test. A refusal is not a failure: `{refused}` writes nothing and the caller keeps its last accepted result (§2.1).
- The bounds hold under every set of rules `resolve` can give, since a rule turned off only skips a phase or takes a branch another phase already has; the property test of step 2 runs them so.
- Step 2 tests the bounds where width, height and FOLLOW feed each other (a text that widens gets shorter and lifts the blocks under it into the rows of another text, which then narrows), on long chains of neighbours pressed aside and down, and on large accepted notes (the generated note of §4.5 and the owner's exported notes), not only on small random sheets.

### 4.3 Measuring (E-3)

```js
/** @typedef {{rows(id:string, cells:number):number, natural(id:string):number}} Measure   // by block id: the browser's measure reads the content through the bridge, the Node stub from a map id → {kind, text, wrap} */
```

- **Browser:** one hidden measuring element per kind, styled with the block's own classes, in the sheet so that the text size and the font are the page's, filled with the same sanitized content the block shows (`cleanRich`). Results are cached by a **measurement signature**: the kind and its options (a code block's `wrap`, `num` and language header, an area's title and `collapsed`); the content as rendered, chips with their resolved labels (`linkChip`, 1898); the width in cells; the text size; the text placement and field (P18); and a font epoch, raised by `document.fonts` when a face loads. A placeholder is never measured (PR-8): an empty text's natural width is one cell.
- **Re-measuring.** A change of a block's signature is a size change of that block (phase 1a). Made by the user in the note (typing, a code toggle), it is an action and writes as §3.4 says. Otherwise it is a view-only re-measure, which shows and writes nothing and has no undo entry; what it moves differs from the stored fields and is written with the next user action in that container (§3.4): the text placement changed in the settings (P18, a device setting in 0.1, which acts on rows as a font does, `LAYOUT-RULES.md` VIEW.6a); a linked note renamed elsewhere, whose chips `liveLinks` (1903) relabels itself, through `linkChip` (1898), when `takeStored` or `takeNote` finds another note changed (1333, 2202), with `renderBacklinks` called beside it and no `relayout`, so today's layout call sites do not see it; a font that loads after the note opened.
- **Two measures.** This function is the canonical measure. The displayed measure is the same function with the temporary heights of `show` answered for their blocks (§2.1), so no other part of the engine knows a temporary height.
- **Node:** a stub: a text of `n` characters is `ceil(n / (cells × 3))` rows and `ceil(n_longest_line / 3)` cells wide; code is one row per line and never wraps unless its `wrap` is set; an area's header is one row unless a test says otherwise; so tests state their expectations in cells.

### 4.4 Passports (E-4)

**One fold.** The engine knows one fold: the rows shown plus one row for «Розгорнути» when the content is longer (SIZE.6). In 0.1 only code has one, read by its passport from its `ch` unless `open`, as today. 0.2 gives every kind that folds one standard stored field and one look and command (A3), so the engine does not change for it.

**Code is elastic as a text (W14).** Today a code block without `cw` takes all the room to its right neighbour (`rawWidth`, `index.html` 2351–2362); in 0.1 it is as wide as its longest line, up to `TEXTW`, like a text, and the user widens it by hand when needed. Nothing stored changes; a code block with long lines looks narrower than today, its lines wrapped or scrolled sideways by its own setting.

A text's measured width and the cell size follow the text size: a larger text size makes `G` larger (`--g`, as `applyText` does today), so the sheet scales and no column or row changes; the measuring cache is cleared. A new kind (a checklist, an image) adds a passport and nothing else in the engine: its minimum, whether it hides lines and its fold are the passport's, and whether it can move is `canMove`'s (§2.1).

### 4.5 Performance

`LAYOUT-MODEL.md` F8 measured today's code at 63 s to open a note of 120 blocks, most of it DOM measurement repeated in three passes. The budgets for 0.1 count the measuring: on a generated note of 120 blocks in two containers, with a cold measuring cache, opening the note under 150 ms and at most one measurement per block and width tried; one pointer move of a carry under 8 ms with a warm cache; one keystroke that grows a text under 4 ms plus one measurement. The engine works per container; FOLLOW and RELINK are linear in the pairs after sorting; a pointer move runs one `settleTree` from `start`. `open()`'s sizes step (§3.5) is the bulk of the measurements on opening. Step 1 measures the engine in Node, step 4 the measuring in Chromium, step 5 the whole in the app. In the browser a budget counts the whole path, the blocks' DOM made, measured and drawn, not the engine alone; every result is recorded with the machine and the fixture it ran on: a generated note of 120 blocks kept in `tests/fixtures/`, on CI's Chromium and on the owner's 14-inch laptop.

## 6. The boundary with `index.html`

The bridge is the only module that reads or writes `index.html`'s block objects. `index.html` changes in four ways only:

1. **Where it lays out today, it calls the bridge.** Each call site of today's layout functions (§6.1) becomes one call: `LAYOUT.change(type, …)` for a user action, `LAYOUT.open()` when a note is shown or changed from outside, `LAYOUT.draw()` when only the look changed. With the switch off the old call stays.
2. **Its gestures for placement are handed over.** The carry by the grip, the arrows of position mode, the width and height handles, the area's handles, drawing an area and the click on the empty sheet are `input.js`'s; `index.html` keeps the gestures that are not placement (selection, entering and leaving position mode from the block's menu, the menus); the long press of position mode on touch is off in 0.1 (W13).
3. **The undo stack gets the engine's entries.** An engine action returns the stored fields before and after; the bridge pushes them as one entry of the existing structural undo stack (C2), so Ctrl+Z, the toasts and the history treat them as they treat any structural change.
4. **Its settings menu gets the engine's switch, the testing look's and, on `.dev`, the «Правила» list** (§1, VIEW.7, VIEW.8). The settings menu (`setPop`, 692–708) gets three device settings, all saved in `sheet:settings` as its other settings are, their labels in `uk.json` and `en.json`: the switch «Нова розкладка (0.1)» (§1); with it on, the testing look's switch (VIEW.7), which `view.js` reads (today the only debug control is `dbgRow`, 721, shown by `?debug=1` at 2087, and it stays); and, under `IS_DEV` (819) with both on, the «Правила» list that `panel.js` draws in the place `index.html` gives it (VIEW.8). A change of the list calls `LAYOUT.open()` for the open note, with the rules resolved again.

Two more rules hold at the boundary:

- **Guards.** An engine action runs only where today's placement code may run: never while the note is read-only (the trash, a version shown in «Історія», the storage lock, a tab turned view-only by a newer format); and the bridge writes through today's pipeline (`markDirty`, `update`, the editor snapshot that sync reads), never around it.
- **Stale gestures.** A gesture held when the note changes from outside (another tab or device), the note is switched or closed, «Історія» opens, the tab turns read-only, the account's owner changes or the «Правила» list changes, ends at once as a cancel (DRAG.C3): nothing is stored, and the layout drawn next is the one `open()` gives. No gesture finishes on a layout that is no longer the note's.

### 6.3 What the user sees change

Every item comes from a decision; the ones that touch the phone are listed so that the owner checks them on a device before step 6.

- **The sheet has a width.** A note's sheet is `SHEETW` columns on every device, with white room to the right on a wide window; a narrow window scales the note by the width it uses, up to its rightmost block, so a note on the left of the sheet stays at full size in a half-screen window (W2, W7, W12, §3.1). Today a sheet block's place is a share of the window's width.
- **Old notes may shift once.** A note whose stored places overlap or stick out at `W0px` is shown separated and clamped (§3.5); those places are written with the user's first action in that container (§3.4), not before. A block whose set width is wider than the sheet is shown as wide as the sheet, its stored width kept.
- **The phone and the tablet move nothing** (W13). They read, write, delete and create blocks by «+»; nothing is carried, resized or moved by position mode, which goes away on touch until the touch stage. On a computer position mode stays, entered from the block's menu, and its arrows jump as today (W15). A phone or a tablet shows the real layout when the note fits it at the minimum scale by the width the note uses (W12), a narrow note even on a phone, and the narrow view otherwise (W6, VIEW.2–VIEW.5). Today both show the free sheet, with position mode on a hold.
- **Touch on the empty sheet** makes no block (W13): a hold shows the borders while it is held (VIEW.6a); a new block comes from «+». Today a hold creates one.
- **The block's «⋯» menu on touch** loses «Виділити», «В область…», «З області» and «Розмір» in 0.1 (W13); copying, deleting, converting, colour and links stay.
- **Hover on the empty sheet** shows the cell cursor only, no ghost of a block (EDIT.2).
- **A «Правила» list on `.dev`** (R1, VIEW.8). In the testing look's settings, every switchable rule with a checkbox, all on; a rule turned off lays the open note out again at once by its fallback, and what that moves is written with the next action in that container (§3.4, §7). `.app` has no list.
- **Pushes are not permanent.** A block that grows and shrinks back leaves its neighbours where they were (H1, G1); today they stay pushed (`LAYOUT-MODEL.md` F3).

### 6.4 Undo

Today's structural undo is one stack per note (`offerUndo`, `index.html` 2618): the toast's button, Ctrl+Z outside the fields and the header's «Скасувати» all undo the top entry (`doUndo`, 2632); a newer entry replaces the toast; there is no structural redo; a change from outside drops every entry that is not marked `safe` (`undoStale`, 2616). The engine fits into it as follows.

- **An entry.** An engine action pushes one entry (C2) with the toast it has today. It carries the stored fields the action wrote, before and after, the canonical layout before the action with its gaps and lends (which may differ from the stored fields, §3.4), and two **state identities**. The bridge gives every canonical layout it holds an identity, a fresh one for every change applied to it: an action, a size change from typing, a view-only re-measure (§4.3), a re-open (a change of the «Правила» list included), an undo. The entry records the identity of the layout the action started from (`before`) and of its result (`after`).
- **Undo with nothing applied since** (the current identity is the entry's `after`): the fields' «before» values and the layout with its gaps and lends are put back, with no SETTLE, and the current identity becomes the entry's `before` again; the layout is exactly the one before the action. So undoing B and then A, with nothing between, takes this path both times: once B is undone, the identity is B's `before`, which is A's `after`.
- **Undo after changes applied since** (the current identity is not the entry's `after`). Only changes with no entry of their own can come between, since a structural action pushes a new top entry: typing that changed heights, a fold, a view-only re-measure, a change of the «Правила» list. Then the undo runs SETTLE, under the rules now in effect, so that nothing overlaps: an undone deletion makes the block again as `create` at its stored cell, in reading order, an area first and its children then entering it; an undone move carries the block back as a drop at its old cell; an undone resize sets the old size; an undone creation removes the block; an undone `enter` is a `leave` back to its old cell and the other way round; an undone `ungroup` makes the area again as `create` and its children enter it at their old cells. This is the rule EDIT.4 states for a new block taken away.
- **No redo**, as today.
- **Changes from outside.** Engine entries are not `safe`: a change from another tab or device drops them, as it drops today's entries, since their layouts are stale.
- `placeUndo` snapshots `collapsed` too, which it misses today.
- An entry passes its `size` to `offerUndo`, counting the layout, gaps and lends it carries, so `trimUndo` keeps the stack within `UNDO_BYTES`.

## 7. Risks

- **Notes made at another width.** Reading `fx` at `W0px` (§3.1) moves sheet blocks of notes made on a much wider or narrower sheet. Mitigation: `W0px` chosen from the owner's measurements (W11); the switch lets the owner compare before step 6; the engine writes nothing until the user acts.
- **Two layouts in one tab.** Between steps 5 and 6 both exist; the switch is read once when the tab starts (§1), so a tab runs one of them only.
- **The current version keeps writing pushes.** Today's `resolveIn` writes pushed rows (`index.html` 2379) and saves them with the next edit; `relayout` does so on every keystroke. Every edit on a device or in a tab without 0.1 (the switch off, or `.app` before the release) keeps sending permanent pushes into notes that 0.1 reads as places. So G1 and INV-7 hold only among devices and tabs that run 0.1; the owner is told before using the switch on `.dev` with notes edited elsewhere.
- **Rows of different fonts.** A device that measures a text taller than the device that wrote the note separates the blocks under it on opening and writes those rows with its first action in that container (§3.4). Otherwise §3.4 writes what an action moved and what that container shows and has not yet written, so a keystroke that changes no height writes no row where the stored places are the ones shown; a keystroke that changes a height writes the rows of the blocks under it, as today, and two devices editing the same note can then make a conflict copy, as today.
- **The text placement variants** (P18) change the insets a text is measured with, so they act on rows like a different font: what a device separates or re-rests because of them is written only as §3.4 says.
- **A larger text size.** `fx` written at a larger text size reads to other columns (§3.1); a current-version tab at a larger text size reads the engine's `fx` to other columns. The owner's answer (§1.3) says whether this touches real notes.
- **Rules switched off on `.dev`.** A rule turned off in the «Правила» list (VIEW.8) changes how every note is laid out on that device: the open note is re-opened by the rule's fallback, and what that moves is written with the next action in that container (§3.4), into the notes on `.dev`, copies of real ones among them, and synced to the owner's other devices there, which lay them out by their own rules. A fallback may give up INV-7 b, which holds only with `GAP.2`, `GAP.5.2` and `GAP.5.3` on (with one of them off, a block taken away does not give its neighbours their gap back whole), so a gap lost then stays lost after the rule is back on. Mitigation: the list is a device setting in `sheet:settings`, never stored in a note, every rule on by default; changing it writes nothing by itself; it is absent on `.app` until the owner decides (§1.2); and the owner is told before using it on notes that matter.
- **A note that cannot be laid out.** Only a bug can make `open()` fail; the note then shows as stored, with placement off and nothing written (§3.5), so such a bug costs moving blocks in that note, never the note.
- **Gestures on the displayed layout.** A drop while a temporary height is in effect stores canonical rows (`LAYOUT-RULES.md` §2.1): the block stays where it was put while the temporary height lasts, and keeps its gaps when it ends; step 5 compares the stored fields with the setting on and off.
- **The structural undo stack and history.** An engine entry must restore exactly the stored fields it changed; tests undo every action and compare the stored blocks.
- **Unknown fields.** 0.1 writes only today's fields, so an older version that edits a note drops nothing of 0.1's. Step 0 of `LAYOUT-MODEL.md` §7 (the editor keeps fields it does not know) moves to 0.2, before the first new field.
